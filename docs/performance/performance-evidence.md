## 固定条件

- 1440×900 CSS 像素，DPR 1，CPU 降速系数 1。
- 下载 10 Mbps、上传 2 Mbps、延迟 40ms。CDP 吞吐单位为字节/秒。不是公网网络实测。
- 落地页 `/`、工作台 `/workspace`、画布 `/canvas?doc=固定ID&benchmark=1&mode=clean`。
- 每页交替采集 cold/warm，每种缓存 3 轮。cold 清空 HTTP 缓存、localStorage、cookie 和 service worker；warm 保留前一轮 HTTP 缓存，清空 localStorage。
- 热访问遵循实际 Cache-Control；`no-cache` 仍可能重新验证或下载，不假设传输为零。每页冷缓存独立，因此没有模拟跨页面共享缓存。

## 指标定义

| 指标 | 定义及用途 |
| --- | --- |
| networkBytes | CDP 完成请求 encodedDataLength 之和，含接收侧协议开销；命中浏览器缓存计 0。排除 SSE/WebSocket，包含 HTML/API/字体/图片/JS/CSS 等实际请求。不是网络抓包的全部上下行字节。 |
| jsNetworkBytes | Script 请求接收字节之和，验证压缩和缓存收益。 |
| jsDecodedBytes | Resource Timing 中 script 的 decodedBodySize 之和，辅助核对实际加载代码量。 |
| FCP | First Contentful Paint，首个内容绘制时间。 |
| lcpObservedMs | 截至观察结束的最后一个 LCP 候选及元素；不是用户离开页面后最终的现场 LCP。canvas 内容不在 LCP 候选中。 |
| clsObserved | 观察窗口内排除近期输入的布局偏移，取最大会话窗口值；不是完整访问生命周期 CLS。 |
| domReadyProxyMs | 落地页标题出现；工作台最近项目区域、textarea 出现且加载骨架消失；画布 bridge 报告 500 个对象、viewport 非零、canvas DOM 存在。之后再等待一次 rAF。该值是就绪结构代理，未证明交互完成或 GPU 实际呈现。 |
| longTaskTotalMs / longTaskBlockingMs | 观察窗口内长任务总时长 / 超过 50ms 部分之和。后者不是标准 Lighthouse TBT，不单独归因于 JS 解析。 |
| navigation / resources | TTFB、DOMContentLoaded、load 及每项资源原始 timing，供瓶颈分析。 |

每轮保存请求列表、状态码、缓存命中、Content-Encoding、Cache-Control、页面错误、浏览器 timing、字体时序、画布对象数量。首次 cold/warm 保存截图。`environment.json` 保存浏览器版本、CPU、内存、工具版本、采集器哈希、源码静态资源与构建产物哈希、场景哈希；当前工作区有未提交改动，单独 HEAD 不能复现源码，应保存对应源码快照。

比较器仅比较相同环境、采集器和场景，排除错误或超时轮次，不足 3 个有效样本时不计算收益；输出中位数和样本范围。3 轮属于初步实验基线，不证明小幅改善显著。正式发布收益建议增加轮数、交替 A/A 与 A/B，记录设备负载，并验证有窗口浏览器。响应协议开销和连接状态可造成字节小幅波动。

尚未采集：真实公网/生产反向代理、真实业务图片视频、INP、实际操作完成时刻、JS 解析/执行的专门 trace、功能首次打开时间。优化相应项前需补齐同场景基线，不能从本报告推算它们。

依据：[CDP Network](https://chromedevtools.github.io/devtools-protocol/tot/Network/)、[CDP Emulation](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/)、[LCP 定义](https://web.dev/articles/lcp)。

### 1. 构建产物体积

本次使用空的临时目录构建，排除了旧文件残留。统计范围是编译生成的文件，不包含直接提供的 HTML、CSS、图片、字体、Python 依赖或容器镜像。

gzip 使用 level 9，Brotli 使用 quality 11。压缩总量是每个文件独立压缩后的合计，用于固定条件下的体积比较。单个页面实际下载哪些文件、服务器是否启用压缩、浏览器是否命中缓存，需要以请求记录为准。

### 2. 网页采集条件与缓存含义

本次采集的是网页桌面端，使用独立的 Chrome headless 浏览器。窗口为 1440×900，DPR 为 1，CPU 不降速；下载限制为 10 Mbps，上传为 2 Mbps，延迟为 40 ms。服务使用隔离的 Mock 配置和临时数据。工作台显示两个文字文档，画布加载固定 500 个文字对象。

冷缓存（cold）表示清空浏览器缓存后打开页面，模拟首次访问。热缓存（warm）表示保留前一次访问的 HTTP 缓存，再次打开同一页面；应用本地存储会清空，以保持文档输入一致。热缓存仍然遵循服务器的缓存策略，资源可能重新验证或下载。

三个页面分别采集三轮冷缓存和三轮热缓存，共 18 轮，全部通过就绪和请求错误检查。下面的时间与下载量均为有效轮次的中位数。每页冷缓存独立，不包含跨页面共享缓存的收益。

### 实现与原因

DocStore 保存对象、关系、位置和属性，命令管理修改与撤销；CanvasView 管理可复用投影；eligibility 判断支持范围；session 管理失效、队列、版本和资源；worker-client/entry 负责后台绘制；React hook 管理订阅、字体/DPR 与生命周期；Konva 图像层负责显示。没有删除所有对象组件，也没有把文档所有权移交 Worker。

### 测试环境与测量口径

10 个场景各 3 轮。每轮重新导航、画布出现后等待 2.5 秒，随后分别静止、鼠标移动、平移、缩放各采样 3.5 秒，自动保存窗口 2.5 秒。保存主线程前处理使用额外复测，并将横跨采样起点的长任务计入；原始首轮 autosave 长任务计数可能遗漏起点前已开始的任务，不用于这些场景的汇总。表格 FPS、P95、P99、长任务数等为三轮各自统计值的中位数，并非混合全部帧重新计算的分位数；完整逐轮数据见 CSV/JSON。拖拽另测每轮 5 秒，并校验保存后的对象坐标；500/5000 对象各 3 份有效样本，1000 对象仅 1 份有效样本（其余 2 份未改变坐标，已排除）。

这里的 FPS 是 requestAnimationFrame 回调频率，属于主线程响应与帧调度代理指标，不等同于 GPU 实际呈现帧率。超过 33.34/50 ms 的帧数是帧间隔阈值计数，不能称为浏览器真实丢帧数量。交互由测试脚本每个 rAF 发出一个 DOM 输入事件，因此低帧率时输入数量也随之减少；不模拟固定 120Hz 指针硬件事件流。主线程卡顿已用 DevTools 轨迹另行核对。此次没有把合成事件统计冒充 INP，也不报告线上 Core Web Vitals。

60Hz 每帧预算约 16.7 ms；33.3 ms 相当于两个刷新周期。长任务使用浏览器 Long Tasks API（超过 50 ms），定义参照 Chrome Performance 文档。报告里的长任务只统计各场景采样窗口；页面加载观测另存于逐轮 JSON 中。

### 基于实测的优化顺序

- 先降低交互更新范围：无变化输入不发布快照；分离相机、选区和文档订阅；对象节点保持稳定引用，按可见范围渲染。首个验收目标是 500 对象、50 张图片的平移/缩放达到现有压测注释要求的 55 FPS，再向 1000 对象扩展。

- 处理后端全量读取和同步保存：文档列表提供独立元数据索引/查询，历史引用增量维护；保存与其他请求隔离，同时保留版本冲突检测和单写入所有权。不能简单移到多线程而放弃并发一致性。

- 减少生产轮询查询：批量预取子任务，按版本/事件增量同步；先消除 N+1，再评估连接数和连接池预算。

- 媒体按需加载：图片分级加载有明确体积收益，视频按可见/悬停控制用于减少资源开销；此次视频没有严重掉帧证据，不应把它作为第一项卡顿修复。

- 保存优化按同步耗时验收：减少全量克隆与重复编码，保留本机草稿和冲突恢复。通过最长帧而非平均 FPS 判断保存尖峰。

### 画布性能采集 V5

目的：让改造前后有相同输入工作量、可追溯原始记录和正确性校验。这个工具采集实测值，不把架构目标当作收益。当前协议 V5 修正回调计数、短操作资格、完成顺序、运行时异常及字体重新检查。V4 曾补齐字体就绪、纯交互分段、页面内完成代理、Long Animation Frames、诊断态 React Profiler 与可测工作量计数。旧协议（canvas-native-v4 及更早）数据不可与本协议混算。

## 运行

需要 Node 22+（全局 WebSocket）、项目依赖、`.venv` 和 Chrome。默认 Chrome 路径为 macOS 安装路径，其它平台通过 `--chrome PATH` 指定。

体验比较（clean，无 React Profiler 探针）使用普通生产前端构建：

```sh
npm run build:web
.venv/bin/python scripts/perf/server.py --port 7815
```

服务绑定 loopback，每次创建独立临时数据目录，显式使用 Mock 配置，不读取真实 Provider 密钥。固定种子场景为 500 和 5000 个文字对象。保留旧数据和旧报告，不与本协议混用（协议为 canvas-native-v5）。

另一个终端采集：

```sh
node --import tsx scripts/perf/run.ts --label baseline --repeats 3 --dpr 2 --out /tmp/canvas-baseline
```

每个场景执行静置、固定输入流平移、固定工作量平移、全选。可用 `--scene text-5000 --action pan` 选测。每次打开全新页面并清空缓存/本地草稿。文档打开、字体就绪检查通过并稳定 2 秒后计时。当前是文字场景的稳态测试，不是冷启动或图片/视频就绪验证。

需要诊断 React `actualDuration` 时，必须使用 React profiling 生产构建；普通 `build:web` 不会启用 profiling：

```sh
npm run build:web:profile
node --import tsx scripts/perf/run.ts --label diagnosis --mode diagnostic --scene text-5000 --action pan --repeats 1 --out /tmp/canvas-diagnosis
```

`build:web:profile` 精确替换 `react-dom/client` 与 React Konva 使用的 reconciler 为 profiling 实现，只用于诊断测量，不要当作要发布的产品构建。clean 体验比较应重新执行 `npm run build:web`。

```sh
npm run build:web
node --import tsx scripts/perf/run.ts --label candidate --repeats 3 --dpr 2 --out /tmp/canvas-candidate
node --import tsx scripts/perf/compare.ts /tmp/canvas-baseline /tmp/canvas-candidate
```

两个结果目录必须是不同目录。结果支持分开机器运行，但比较器会检查环境与场景兼容性。协议、采集器、DPR、Chrome、机器或 React profiling 构建标志不一致时拒绝收益百分比。正式评估应交替跑旧/新构建，至少 3 轮；短样本只用于诊断，不宣称统计显著。记录同一设备负载、供电、刷新率和温度状态，避免边跑全仓测试边做正式测量。

## 输入与有效性

- 输入由浏览器外部的 Node 时钟通过 CDP 发送，产生真实、可信的浏览器事件。
- 平移固定 60 次移动、120×60 屏幕像素、约 3 秒轨迹，输入次数不依赖页面 FPS。
- 输入调度不等待 CDP 的传输确认。确认延迟只记录为运输诊断，不当作页面处理时间。
- 外部调度超过 100ms 期限时不追赶突发发送；标记节奏不合格，保留全部记录。
- 固定输入流平移允许浏览器合并中间移动，但实际坐标必须是发送轨迹的有序子集，起止操作次数及最终位移必须正确。报告实际观察次数，不能把事件合并误判成采集失败。
- `pan-work` 逐次等待确认并核对页面已观察到该移动，要求完整60次输入。它没有固定输入节奏，只比较固定工作量完成代理耗时，不比较其FPS。
- 隐藏页面、非可信输入、轨迹不符、动作未生效、字体未就绪时不计算体验收益。
- 输入节奏超过期限时，固定输入流FPS比较无效。固定工作量及全选的完整结果通过校验后，独立比较完成代理耗时。

浏览器运行在独立临时 profile，使用它自己公布的随机调试端口，明确设置前台和焦点，结束后关闭自身进程。不会连接用户已有浏览器调试端口。默认 headless；它是可重复测试环境，不代表所有有窗口/GPU设备的绝对表现。

## 无探针与诊断分开

`clean` 模式不包装业务/绘制函数，也不订阅机制计数器，不挂载 React Profiler；有低开销 rAF、输入、页面内版本时钟和 PerformanceObserver 采集。它仍不是完全零扰动，正式比较必须使用相同采集器。

```sh
node --import tsx scripts/perf/run.ts --label diagnosis --mode diagnostic --scene text-5000 --action pan --repeats 1 --out /tmp/canvas-diagnosis
```

`diagnostic` 额外提供：

- `documentNotifications`、`viewNotifications` 的动作窗口内次数。
- `Konva.Layer.drawScene/drawHit` 的准确调用数、累计包含内部调用耗时、单次最大值。
- Chrome CPU `.cpuprofile` 文件，用于采样定位函数/调用栈；CPU采样并不是每个函数准确调用次数。
- 画布 ContentScene 的 React Profiler 提交次数、`actualDuration`（仅 React profiling 构建有意义）以及对象组件更新次数。未启用 profiling 构建时 `actualDuration` 为 null，并记录原因。

诊断模式不计算体验收益百分比。以后新增投影/缓存计数器时，只在诊断模式接入；没有采集的字段保留缺失，不填 0。当前绘制计数覆盖该 Konva 后端；更换后端必须给新后端增加对应计数，不能用“旧函数消失”证明总绘制工作消失。

## 输出和指标含义

每轮输出 JSON、动作完成后的截图，诊断另有 CPU profile。环境文件记录浏览器版本、CPU、内存、DPR、场景 checksum、源文件/构建/采集器 hash、是否为 React profiling 构建。JSON 保留每个帧间隔、分段窗口、原生输入、计划/实际发送/确认时刻、Event Timing、长任务、Long Animation Frames、字体就绪、工作量计数、页面内输入/视图通知版本、初末状态和无效原因。所有 PerformanceObserver / rAF 时间为毫秒。本工具不做线上上报。

采集窗口：

- 纯交互分段：从首个页面输入（无输入的 idle 则为整段静置）到 `markActionEnd`。检查动作的两次 rAF 收尾和 300ms 收尾不得计入该分段。
- 完成检查分段：`markActionEnd` 之后的两次 rAF 机会。这是完成代理，不是 GPU 呈现，也不是像素真正上屏。
- 收尾分段：两次 rAF 之后的 300ms settle。idle 没有这两段收尾。
- 全窗口 rAF：start 到 stop，包含收尾，仅作兼容对照，不能当作纯交互帧率。

指标：

- rAF FPS / P95：页面帧推进代理及间隔，不是 GPU 呈现帧数，也不是某函数耗时。比较体验节奏时优先用交互分段。
- CDP 完成耗时：从输入开始到序列结束及两次 rAF 机会，含固定轨迹时间与 CDP 通信开销。
- 页面完成耗时：同一两次 rAF 机会的页面内时钟，用于区分 CDP 往返；仍不是像素呈现时刻。固定 60 次输入并不保证渲染了 60 帧。
- 页面内 input/view version：`dispatchInput` 与视图快照通知的单调计数，用来对照“浏览器已处理”和“CDP 已确认”。
- Event Timing：阈值为 16ms，数据有量化；最大观察值不是线上 INP，本协议不计算伪 INP。未观察到记录是 null，不代表 0ms。参考 [INP 定义](https://web.dev/articles/inp)。
- Long Tasks：保留。不支持时为 null。
- Long Animation Frames：`PerformanceObserver` 的 `long-animation-frame`；记录支持检查、blockingDuration 和 scripts 归因。不支持时为 null，不能填空数组冒充“没有长帧”。参考 [LoAF 定义](https://developer.chrome.com/docs/web-platform/long-animation-frames)。
- 工作量：对象总数、视口 AABB 相交数、当前渲染器挂载的绘制候选数。当前 ContentScene 仍遍历全部对象，因此候选数等于存在的对象数。Konva 实际绘制列表未仪器化，`actuallyDrawnCount` 必须为 null。
- JS 堆：操作前后的描述性数值，不包括全部位图、媒体、GPU 内存，不证明泄漏。
- 不支持的指标为 null，不能当成 0。

比较器核对场景、轨迹、初始相机/选区/视口、DPR、Chrome 版本、机器、采集器、协议和 React profiling 构建标志。条件不一致、样本不足、诊断样本、缺测指标会拒绝计算收益比例，同时保留实测数值及原因。相对变化不表述为已验证的优化收益。

当前覆盖文字画布的固定输入流、固定工作量平移与全选。冷启动、素材解码、视频、导出、保存、长时内存回收需要独立场景协议，不能从此处推导收益。V3 及更早的结果不能纳入 V4 比较。

## 方案证据审计（2026-10-02）

结论：V4 可以作为文字画布稳态交互的实验室采集协议。它补齐了 V3 审计中列出的若干证据缺口，但仍不能视为完整前端性能覆盖，也不能据此宣称架构改造收益。动作校验通过只表示满足当前协议，不表示所有指标已经完备。

| 方案判断 | 当前证据 | 结论边界与下一项验证 |

### 与前端及画布指标的对应

- 页面加载：尚未采集 LCP、CLS 和文档可交互时间。Canvas 文档就绪需单独定义业务里程碑，不能假设 LCP 等于画布内容就绪。
- 离散交互：已有阈值 16ms 的 Event Timing；不是页面生命周期 INP，也不覆盖连续拖动全过程。
- 连续画布交互：交互分段 rAF 间隔分布是帧推进代理；不是实际呈现帧。全窗口 rAF 仍包含收尾，不能与交互分段混算。参考 [rAF 定义](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)。
- 长时间阻塞：Long Tasks + LoAF（有支持检查与脚本归因）。尚缺 Chrome Performance trace，不能从 CPU profile 单独还原布局、绘制与 GPU 呈现。
- 组件更新：诊断态 React Profiler；生产测量需 profiling 构建。
- 内存：尚缺重复循环与 [堆快照对比](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots/)。

### 收益发布条件

1. 未测量的瓶颈写为假设。V5 首项优化仅包含文档投影复用、对象组件 memo 和选区 Set 查询；离屏缓存、Worker、空间索引尚未实施。

3. 新旧协议不混算。比较器在不合格/不兼容时拒绝收益百分比。
4. 正式评估交替执行 A/A 和 A/B，预热与缓存政策一致，显示每轮数值及波动。现有 3 轮中位数仅为初步描述，不能证明小幅改进显著；首轮正式实验建议每组至少 10 轮，并根据波动增加样本。
5. 使用有窗口浏览器验证用户体验，记录显示刷新率、供电及设备负载；headless 结果单独报告。
6. 优化需同时满足结果正确、体验指标改善、目标工作量减少，并检查内存及其他场景没有明显退步。截图目前用于审查，不是自动视觉一致性证明。
7. V5 已有独立基线与 candidate；只能发布同协议、同条件的实测变化，不能把本轮文字场景变化推广到图片、视频或总内存。

Codex 复核补充：view version 仅计数视图通知，不证明 React 提交、Konva 绘制或像素呈现完成。lastInputProcessedAtMs 在编辑器输入处理返回后记录。分段帧间隔只纳入起止均在分段内的完整间隔，跨边界间隔保留于全窗口。字体检查目前针对文字基准的 Arial/sans-serif，不验证任意文档字体。

### 首批实现与浏览器复核（2026-10-02）

实现由 Grok 在专用工作树完成，Codex 复核并修正 profiling 模块替换、Profiler 在 React Konva 内容树的位置、通知版本命名及跨分段帧间隔。未修改产品渲染架构。

实际 Chrome 采集24轮 clean 均通过当前协议校验（500/5000文字 × idle/pan/pan-work/select-all × 3轮），clean React探针为null，profiling构建标志为false。5000文字固定输入流的纯交互帧回调频率中位数17.61/s、帧间隔P95中位数66.80ms；完整60次移动CDP完成代理中位数4281.18ms。这里只建立V4基线，不与V3计算变化，也不是优化收益。

独立profiling诊断一次5000文字/完整60次移动：ContentScene提交67次、对象组件函数执行335000次、actualDuration累计757.50ms、LoAF 62条；实际观察60次移动，字体就绪，校验通过。组件函数执行数可能包括未提交的渲染尝试，不代表Canvas重画335000次。该单轮数据证明当前路径有大量内容组件执行，不能代表普遍分布，也不能与clean耗时混算。

一次页面导航时观察到旧页面flushOnUnload的Failed to fetch，发生在新动作采样前；它不计作本轮交互耗时，后续保存/导航场景需独立验证。当前未实施缓存、裁剪、Worker、内存快照、完整Web Vitals与GPU呈现采集。


### V5 修复与首项优化（2026-10-02）

- 帧回调次数独立计数，跨分段间隔不影响回调次数；P95 仍只使用完整位于窗口内的间隔。
- 全选、固定工作量仅比较完成耗时；短操作不计算帧率收益。
- 最后输入、输入处理或输入版本发生在动作结束之后的样本无效。
- 活跃动作期间页面异常使样本无效；开始测量前重新检查字体，拒绝/超时不能作为字体就绪。
- 零基线报告绝对变化，禁止 NaN/Infinity 或无限收益。

首项落地保持现有 DocStore、Konva 和存储格式：CanvasView 在文档没有通知变化时复用投影；每次文档通知使缓存失效。ObjectNode 通过 memo 避免纯相机移动执行全部对象组件，文档投影身份作为版本信号，确保原地修改对象、撤销/重做仍刷新。选择查询改为 Set，预览保留独立覆盖，媒体 hook 自身状态仍更新。并未减少持有的 Konva 对象数量，也未实现按对象的文档脏更新。

初次 clean A/B 各 24 轮均有效（每项 3 次）：5000 文字平移的交互回调频率中位数 18.40 → 39.15/s，间隔 P95 66.70 → 33.50ms；完整 60 次移动页面完成代理 4068.20 → 3161.10ms；全选 163.60 → 95.50ms。500 文字平移已约 60/s，完整工作量 1162.00 → 1179.10ms，小幅波动不宣称改善。后续交替复测数据及每轮记录保存在 native-v5 报告目录。

独立 profiling 各一次完整 60 次移动：ContentScene 均提交 67 次，操作窗口内对象组件执行 335000 → 0 次（初始挂载在窗口外），内容层 actualDuration 累计 756.10 → 200.40ms。它说明被省去的工作，不用于发布 clean 耗时收益。0 次对象组件执行不等于 0 次 Canvas 绘制。

交替复测：旧→新连续三轮，每轮均用新页面、相同种子/DPR/Chrome、clean 构建和 V5 采集器；每边 12 组全部有效。5000 文字纯交互回调频率中位数 18.10 → 42.92/s，间隔 P95 66.80 → 33.40ms；完整 60 次移动页面完成代理 4251.20 → 3154.60ms（缩短 25.8%）；全选 164.70 → 88.90ms（缩短 46.0%）。这是本机 headless 的三轮实测变化，不是统计显著结论或所有设备保证。前一组 24 轮实验仍完整保留，不能挑选某轮更好的值作为总体结果。

### 最终架构方向与当前落地边界

| 模块 | 职责 | 当前状态 / 收益验证 |
|---|---|---|
| 文档数据 DocStore | 保存对象 id、类型、位置、尺寸、内容、关系与顺序；处理命令、撤销与持久化 | 保留现有格式，文档通知使投影缓存失效；纯相机移动不修改文档 |

| 当前 Konva 渲染适配器 | 创建图形节点，更新属性和绘制 | 已 memo 对象组件，选区用 Set；仍保留每对象 Konva 节点及整体内容遍历 |

| 后续变更集与空间索引 | 按对象记录变更，查询可见对象及命中候选 | 未实施；必须检查移动、缩放、删除、关系、跨视口、撤销等边界 |
| 后续脏绘制与离屏缓存 | 复用静态绘制结果，只重画受影响的旧/新范围 | 未实施；需记录失效、命中、重画面积与位图内存，字体/DPR/缩放/视频变化须失效 |
| 后续 OffscreenCanvas Worker | 把可转移绘制任务移出主线程 | 未实施；先确认剩余绘制瓶颈，再测消息排队、复制成本、取消/销毁与兼容回退 |

诊断仍显示 drawScene 60 次累计 1198.10 → 1131.40ms、drawHit 60 次累计 297.50 → 303.50ms。它们来自各一次 profiling 诊断，说明 Canvas 绘制仍占较大工作量，不能用它们宣称绘制已优化或计算体验收益。下一步的可见裁剪、脏绘制、离屏缓存应针对这部分工作，并独立建立 A/B 开关。

现有回归覆盖投影复用、相机更新、原地文档修改、删除、撤销；已有前端测试继续覆盖编辑器逻辑。文字基准不证明图片加载、视频播放、素材回收或内存泄漏改善。操作前后堆差值保留为描述性数据，不给出内存收益百分比。

### 原始性能数据采集（第一阶段）

本阶段交付采集、关联、落盘、导出与核对。不包含管理后台，不会向第三方发送数据。
实现采用本地 `schemaVersion=1` 事件协议，以及 HTTP `traceparent` 关联；**不是完整 OpenTelemetry SDK / OTLP 实现**。以后接 Collector 或管理后台需要适配导出格式。

## 安全运行与复现

在独立 worktree 执行：

```sh
npm run verify
SWARMUI_TELEMETRY=1 .venv/bin/python scripts/perf/server.py --port 52108
```

该 fixture 自动设置独立 `SWARMUI_CONFIG`、`SWARMUI_DATA_DIR` 并选择 Mock，不读取真实 Provider 密钥。记下启动输出的 `Isolated mock fixture data` 目录。

另一个终端运行真实浏览器输入：

```sh
node --import tsx scripts/perf/tile-edit.ts --base http://127.0.0.1:52108 --renderer worker --cache-layout tiles --telemetry on --out /tmp/telemetry-proof
```

该脚本打开全新 Chrome profile，读取 5000 文字对象，放大、双击、输入并提交 12 次，再重新打开文本框核对结果。随后从浏览器并发提交 3 个 Mock 请求（生成请求是程序调用，不是用户体验测量），观察任务完成和 SSE 收到状态，再发一次预期 404。退出时核对缓存资源账本并排空采集队列。

停止该隔离服务器，确保 writer 正常排空，然后导出：

```sh
.venv/bin/python scripts/perf/telemetry-export.py --data-dir /tmp/aivideo-benchmark-实际目录/data --proof /tmp/telemetry-proof/telemetry-browser.json --out /tmp/telemetry-proof/export
```

输出 `events.jsonl` 和 `summary.json`。核对器检查 schema、事件唯一性、采集缺口、前端请求→API→job→各阶段的父子关系、会话、执行次数，以及任务完成状态的浏览器收取记录。服务正常退出时保存 `final-status.json`，独立目录且没有轮转时，核对最终 `written` 与文件行数相等。校验失败返回非零退出码。没有 `--proof` 时只验证原始文件，不证明场景覆盖。

普通页面用 `?telemetry=1` 开启前端。后端另需 `SWARMUI_TELEMETRY=1`。两边默认都关闭。`window.__aivideoTelemetry.snapshot()` 查看队列与支持情况，`flush()` 请求上报；HTTP 200 不等于数据全部落盘，须看 ACK 和后端计数。完全关闭前端采集需移除参数并刷新；`stop()` 会停止本地定时器与回调上报，但 Web Vitals SDK 没有完整卸载接口。

## 场景与数据含义

| 场景 | 原始数据 | 能说明什么 / 不能说明什么 |
|---|---|---|
| 页面加载 | `browser.web_vital` 的 LCP、FCP、TTFB、CLS | 官方 web-vitals 算法；LCP 不是 Canvas 所有对象画完的时刻；CLS 无单位，其余为 ms |
| 点击、键盘等交互 | 官方 INP；`browser.event` 原始输入等待/处理时间 | 两者分别记录，最大 Event Timing 不当作 INP；拖拽流畅度另看帧推进 |
| 画面卡顿 | `browser.longtask`、`browser.loaf`、`browser.frame` | 长任务、长动画帧、每秒窗口的最大 rAF 间隔；不是 GPU 帧率 |
| 打开文档 | `canvas.action`，`action=open, phase=json_ready` | 到文档 JSON 读取解析完毕，未包含创建视图、布局、上屏 |
| 修改文字 | `canvas.action`，`action=edit, phase=commit` | 同步命令执行耗时，不含后续 React/Konva/Worker 完成 |
| 离屏缓存维护 | `canvas.renderer` 的阶段累计值、对象计数、缓存资源账本 | 同一渲染会话累计值，不能把每秒快照相加；当前细分阶段只覆盖 tiled 路径 |
| Worker 绘制 | `canvas.worker` 的 `workerDrawWallMs`、`sendToReplyMs` | 前者来自 Worker 本地计时，后者在浏览器计时；不跨时钟相减；不是 GPU 时间 |
| 接口 | `http.client`、`http.server` | 均到响应头，未包含整个 body 下载或长连接持续时间 |
| 生成任务 | `queue.wait`、`provider.generate`、`artifact.persist`、`job.total` | 排队、等待 Provider、保存素材、任务全过程；嵌套时段不能简单相加 |
| 结果状态回到页面 | `generation.received` | 收到相同任务状态，按 job+attempt+status 去重；不等于图片解码或像素可见 |
| 页面内存 | `browser.memory` | Chromium `performance.memory` 的近似 JS heap，不代表全部页面/GPU/Worker 内存 |
| 缓存内存 | `canvas.renderer` 的 cacheBytes/reservedBytes | 按位图尺寸计算的 RGBA 估算；不是进程实占 |
| 后端 CPU / 内存 / 忙碌 | `runtime.cpu/memory/event_loop` | CPU 是进程 CPU 累积时间的区间差，内存是进程历史峰值 RSS，忙碌是约 1 秒定时唤醒延迟 |

所有阶段耗时用各自进程/线程的单调时钟计算；`startedAt` 仅用于近似时间线，不用于跨机器相减。同步代码片段墙钟不是操作系统 CPU 时间，Worker 与主线程阶段可能重叠。

Web Vitals 使用 `reportAllChanges=true`。同一 `sessionId + metricId` 的后续回调是更新快照，取最新值，不求和、不当作多个独立用户样本。页面仍打开时值可能继续变化。`capabilities` 说明支持情况，`observedMetrics` 说明是否真的收到 SDK 回调；未收到不能填 0。原生 `browser.paint` 的 `value` 是从导航开始起算的绘制时间点，不提供恒为零的 `durationMs`。

## 可靠性与边界

- 浏览器缓存最多 512 条（包括上传中的记录），单批最多 100 条 / 48 KiB，5 秒超时，最多尝试 3 次。重试沿用 eventId；ACK 单独计算 accepted、duplicates、dropped。
- 后端队列最多 2000 条，上报限流 200 条/秒、突发 400 条；单批最多 64 KiB。白名单拒绝业务文本、未知字段、任意 URL。记录文件最多约 5 MiB × 3，轮转会淘汰旧数据。
- `accepted` 是入队，`written` 是成功写入；写盘失败单列 `writeDropped/writeErrors`。无在途写入时可核对 `accepted = written + writeDropped + queued + inFlight`。运行期状态快照不是原子事务；写入累计值包含已被轮转淘汰的文件。成功写入不承诺断电后仍持久（没有逐批 fsync）。
- 浏览器关闭、崩溃、网络永久失败仍可能丢失尾部数据。页面内丢弃计数不能替代服务端独立送达监控。当前是显式诊断采集，未承诺无损分析或生产 SLO。
- SSE 收取去重缓存最多 1024 项；页面刷新或超出保留窗口后不保证全历史去重。不同页面的任务不归入本页面会话。
- Worker 每个请求有独立 trace，能关联到页面 session；**尚未归因到某次具体文字编辑**。渲染累计快照也不作为某次操作的独占耗时。
- 本轮后端覆盖单进程 FastAPI + Jobs；`production.py`、Celery、多进程队列、数据库查询/连接池、具体外部 HTTP 子请求未接入。
- GPU 显存、Worker 独立堆、图片解码到上屏、长时泄漏、采集探针的稳定开销、线上用户百分位仍待独立验证。已有 CPU profile / 堆循环基准继续使用 `README.md` 中的诊断脚本。

官方口径参考：[web-vitals](https://github.com/GoogleChrome/web-vitals)、[W3C Trace Context](https://www.w3.org/TR/trace-context/)、[Performance.memory 限制](https://developer.mozilla.org/en-US/docs/Web/API/Performance/memory)。
