1. 产品定位与首版完成标准

一个以画布为文档、让用户通过直接操作与受限创作助手生成、加工和整理视觉素材的平台。首批服务开发者本人和体验者，商业用户画像仍待验证。

首版完成标准：用户从工作台进入“我的画布”，创建、命名并重新打开同一文档；完成一轮四方向图片生成；选取图片，经蒙版确认得到相邻的透明图片；通过一次带显式引用的助手操作完成同一闭环；下载原始素材。刷新、断线、失败和离开页面后，已保存内容与已产生资产可恢复，未知请求不会被自动重提。

真实四方向生成、蒙版编辑质量和 Agent 模型调用需要分别验收。交互演练中的示例图片、状态切换与本机存储只用于评审，不能替代这些验收。

5. 四方向生成

5.1 方向与提交

输入区提供“生成图片 / 创作助手”模式，本轮建议默认生成图片，避免任意文字被模型自行决定为付费生图。用户输入需求、选可用尺寸/比例后，点击“生成 4 张”。数量固定显示“4 个方向 × 每方向 1 张”。

本轮建议由文本规划器输出四条结构化方向：共同主体、硬约束、方向标题、变化维度、具体提示词。四方向围绕构图、光线、场景或表达方式变化；用户指定的风格和主体不能被强行替换。完整描述可在任务详情展开；首版不增加必须预审四条提示词的步骤。方向规划失败则整组失败，不调用图片模型。示例方向名称仅帮助理解，不是固定四风格模板。

“不同 seed”不足以证明“四个方向”。上线前使用一套版本化评估集验证共同约束与方向差异；建议起始 10 个需求、40 张结果，逐组人工标记“主体/硬约束是否保留、方向说明是否不同、图像是否体现差异”，不编造已通过比例，不自动花费调用进行质量重抽。

8. 视频与下载

首版视频资产路径：已验证文生视频入口 → 平台资产 → 导入资产 → 当前画布对象。文生视频没有源图时显示“来源：文字描述”；不能凭选中图片伪造为图生视频。保存任务、提示词、产物与使用该资产的文档关联。已有视频对象用海报帧、时长、文件格式与来源辨认。

单击选择视频对象，拖海报外框移动；“播放预览”打开带原生控件的预览层。关闭停止播放，焦点返回原对象；播放器内拖动进度不移动画布。首版不做内嵌多路自动播放。

图片和视频下载原文件，透明结果固定 PNG；返回的是资产文件而非截图或棋盘格。开始下载反馈“已开始下载”，不宣称用户已成功保存磁盘。文本和画板仅随文档保存，不能误显示图片下载可用。

9. 保存、恢复与可观察验收

保存状态与任务状态独立：文档可以已保存但图片仍在生成。建议 1 秒防抖提交文档操作；本机草稿先持久化，服务端确认 revision 后才显示“已保存”。本机草稿写失败时明确提示刷新会丢失当前修改，不能承诺离线全量恢复。大图片、视频不内嵌文档 JSON。

SSE 断线后先恢复同一文档快照与任务，再按事件游标补齐；重复事件按唯一结果键忽略。离开页面不取消已接受任务。服务重启且供应商结果未知时查询原 requestId，不自动重发。双标签冲突用 revision 检测，保留本机草稿、重新加载服务端版本；不使用最后写入静默覆盖。

2. 推荐技术栈、替代方案与工程边界

Browser：原生 JS + Konva，DOM 承载导航/对话/工具栏/textarea/video
   │ /api/v2 REST + 单文档 SSE
Python FastAPI API ── Domain Operations ── SQLite + Event/Outbox
   │                                   └─ 文件资产/缩略图/蒙版
   └─ 独立 Python Worker ── Provider Adapters / 有限 Agent Planner
                         └─ rembg 推理进程 + Pillow 合成

FastAPI + Pydantic 用于请求/响应、工具输入和 OpenAPI 契约；HTTP 客户端建议 httpx，SQL 访问可从标准 sqlite3 + repository 开始，迁移规模增长后再用 SQLAlchemy/Alembic。采用锁文件固定验证过的 Python/依赖版本，不在方案阶段猜测某一最新版本兼容全部模型。 FastAPI BackgroundTasks 可执行响应后的小任务，不能直接充当本项目持久队列；官方对重计算也建议考虑独立执行工具。任务恢复、幂等和落位仍由本项目实现。FastAPI 官方说明 SQLite WAL 适合当前单机范围：读写可并行、仍只有一个写者；数据库不放网络共享盘。建议 foreign_keys=ON、busy_timeout=5000、短事务，持久性优先时用 synchronous=FULL 并实测。WAL 官方约束 替代取舍：PostgreSQL + Redis/Celery 在多机器 worker、持续写竞争或多用户扩展时再引入；原生 JS 维护成本确实升高时可单独评估 React，不与此次 API/任务迁移绑定。保留 Express + Python 工具服务最便宜，但不满足“Python 承担核心领域”的推荐目标。 服务暴露首版默认本机；API 密钥只在服务端 credential registry，日志/计划/文档只存 credentialRef 和配置版本。能力检查必须区分 configured、reachable、verified；有 Key 不等于鉴权或模型能力已验收。

3. 数据定义与最小数据库约束

资产是不可变媒体；画布对象是媒体/文字/画板在某文档的实例；任务是执行意图；结果组是四个创意槽；派生图插入显示序列但不扩充四槽。会话、消息、ToolCall 保存引用和来源，不能把来源仅编码在文件名或坐标。 下列是核心 DDL 蓝图，可作为迁移起点；上线前需在所锁 SQLite 版本执行验证。UUID 形状、URL、JSON 内联合类型与跨字段语义由 Pydantic/domain 补充校验。SQLite 的外键需要每个连接显式启用。官方外键说明

5. 幂等、修订与任务落位

5.1 创建意图与 body hash

前端在网络请求前生成 operation UUID、持久本地 pending 记录，所有同一次重试复用同 key。按钮禁用减少误操作；真正去重在服务端，不依赖前端 loading。相同 scope/key 的 body hash 不同返回 409 IDEMPOTENCY_CONFLICT。 规范化 body：先按 schema 校验/填默认值，规范名称的 trim；键按固定顺序序列化，对数组保持顺序；hash 包含操作类型、API contract version、documentId 和实质输入，不包含时间戳、traceId、baseRevision 等运输重试字段。原始 body 与 canonical form 都有版本说明，避免部署后默认值改变导致同 key 被误判。 baseRevision 作为并发前提单独核验：第一次尚未执行且发生 revision 冲突，保留 operationId 和意图 hash，允许用户/前端重取基线后以相同意图重新提交；一旦 applied，则先返回既有 ACK，不再检查当前 revision。body 的实质命令改变须新 key。 POST /documents 在事务中创建 document+operation+conversation，commit 后才回复。响应丢失可查 key；查无记录但原请求仍可能在途时，复用同 key 重发也只能创建一份。操作记录与创建资源同生命周期保存，不能几分钟 TTL 到期就重新允许执行。

5.2 前端 revision 与后台完成共存

前端状态分 serverSnapshot + pendingCommands + transientUI，最终画面为按序重放 pending；transient 包含选择、加载动画、画笔预览，不直接污染服务端文档。推荐 1 秒防抖、笔画结束存草稿，具体目标经性能试验确认。 服务端 BEGIN IMMEDIATE→核对 document revision→应用命令→revision+1→写 operation ACK 与 event_outbox→COMMIT。SQLite 事务保证的是该连接中的本地修改原子性；上游 HTTP 不能放在事务中。SQLite 事务文档 409 时保留本地草稿，拉新 snapshot；拖动 delta 可针对未删除对象重放，文字/名称等覆盖型编辑先按对象 revision 检测，冲突明确展示原/本地内容，不静默覆盖。连续移动/缩放只在前端合并，ACK 顺序不能靠响应到达顺序猜测。 “已保存”条件是最新本地 revision 对应命令全部 ACK。旧快照保存成功但存在新 pending 时保持“保存中”；后台新结果也在服务器 revision 中。beforeunload 只作尽力 flush，可靠返回按钮要等待 flush Promise/ACK；失败留页面或明确放弃。

5.3 创建四图任务与落位原子性

第一笔事务建立 Operation、父 Task、ResultGroup、四 Slot、四稳定 placeholder object、用户 Message 和回复引用；worker 只领取已 commit 的 task。占位使用预生成 ID，事件先于 HTTP 响应时也可按 operationId 对齐。此时方向字段可为显式未规划状态；planner 完成后同事务填齐四方向并冻结，planning 未结束前不得派发图像请求。 worker 保存产物时先写临时文件→解码、尺寸/MIME/hash 校验→原子 rename→事务写 Asset/Slot。发生崩溃的孤儿文件可回收，已持久 Asset 不需重复下载/生成；数据库不得引用未完成 rename 的文件。 四槽确定终结后，短事务统一发布组状态、替换 placeholder、计算布局、更新 document revision、写 Message 引用、Placement 和 event。task 完成且 placement 未完成要显示两种状态；数据库重试只能重落位，不重调用模型。 UNIQUE(task_id,output_index) 防止重复落位；placements.status 阻止完成事件复活撤销对象。输出已生成但源图删除时为 needs_placement，Asset 保留；用户显式“加入画布”创建新的放置 operation，不改写原已撤回记录。

6. Atomic outbox、SSE 游标与恢复

本方案 event_outbox 同时是已提交领域事件日志；API/worker 只在业务事务内插入，SSE 从表按 sequence 读取，不靠内存 EventEmitter 作为唯一来源。首版无需消息中间件；以后增加消息分发才另加 delivery cursor，不要把某客户端收到当作全局已消费。 快照过程：在同一个只读事务视图内读取 document、对象、组、依赖任务、会话摘要和 MAX(sequence)，一起返回 eventCursor。随后订阅 after=cursor；期间发生的更新都在日志中，可以补发，不存在“先取快照再注册回调”漏事件窗口。 消息格式如下；MDN 定义了 id/event/data、自动重连和重试间隔，但不提供本项目数据库持久或业务去重保证。MDN SSE 说明

id: 242
event: group.updated
data: {"documentId":"doc-a","entityId":"group-1","entityVersion":4,"documentRevision":19,"operationId":"op-a","status":"completed"}

SSE 连接按当前 documentId 过滤，心跳注释建议 15 秒；同一个页面只开一个文档流。首次重建 EventSource 用 query after；原生重连可读 Last-Event-ID，服务端验证它属于有效水位。反向代理关闭流缓冲，设置 no-cache，不为每次进度新建连接。 客户端记最后已应用 sequence，并按 entityVersion 忽略旧事件；通知包含足够的小型 patch 或要求重取 entity 的 revision。重复/乱序通知不得直接 append 图片对象。完整实体因离线跨版本时优先快照恢复。 建议事件保留 30 天或可配置空间上限，水位过期返回 reset_required；Task/Slot/Placement、文档和关键工具记录不能随事件短保留期丢失。活动任务列表仅用于徽标，不用于判断完成/丢失；恢复查询文档依赖的具体 taskId，避免最近 100 条截断问题。 服务全部离线只承诺当前内存/IndexedDB 已缓存内容，原文件未缓存则显示不可读；前端不在此阶段增加全量 Service Worker 离线产品。草稿写失败要明确提示，不能假称刷新可恢复。

7. 四方向能力、整组调度与部分失败

7.1 能力合同与阻断门槛

{"providerId":"configured-profile","revision":3,"textToImage":true,
 "creativeGroup":{"count":4,"distinctPromptPerSlot":true,
 "mode":"parallel_requests","maxConcurrentRequests":4,"verified":false,

合法 mode 为 native_multi_prompt_batch、parallel_requests、unsupported；配置值和真实证据分开。当前 Cloud capacity=2、ComfyUI=1 且接口单输出，全部视为新四方向能力未验；Mock 可验证流程但不能被选为真实发布验收。旧生成实验入口可保留明确标识，新入口禁止悄悄用它降级。 “原生 n=4”只有在确实接受四个不同方向的条件或可证明生成方向表达时才合格；一个 prompt 加四 seed 不自动合格。Python 并发 HTTP 也只能证明同时派发，不能证明第三方 GPU 同时运算。 建议验收定义：同一个调度窗口不等待任何结果就发出四方向请求，或一个可验证的四方向原生 batch；保留 dispatch/accept 时间和上游 ID。这是本轮对“同时生成”的工程验收解释，不是对既有约束的静默放宽。供应商内部推理是否重叠仍待验证；若需证明这一层，必须做有可观测 worker 的 Provider 实验，不从 HTTP 推断。

7.2 方向规划与执行

planner 输出 {commonConstraints, directions:[{index,title,variationAxis,prompt}]}，必须正好四项且 index 0..3；固定主体、用途、用户明确限制，变化构图/光线/场景等允许轴。冻结规划 JSON 后才派发图像请求；失败则整组 planning_failed，无图像副作用。 首版不用用户预审四份复杂表单，但可展开方向说明；重新生成同需求的一组复用固定方向快照，新 seed 可不同并记录。编辑需求则新规划。质量需要人工看实际结果，不能仅验证 JSON 不重复就宣称四方向合格。 调度先检查 Provider profile 最大能力；不足 4 且无 native batch 的任务应 capability_unavailable，不能永远排队。并行 mode 领取整个组的 4 个容量许可；不足时整个组等待，不能先跑两张再等两张。单 worker 首版可用内存加持久租约，重启按未知请求保守占用对账。 有多个调度器时，Provider lease 的加权预留要在短事务内核对 sum(active weight)+requested <= capacity，一次申请 4 或一次全拒绝；不顺次 acquire 四个 semaphore 造成半组占有。配额、速率限制和供应商并发是不同限制，需分别处理。 并发协程独立捕获可恢复错误，完成一个槽不停止其他槽；gather(return_exceptions=True) 或 TaskGroup 子任务边界捕获可用。TaskGroup 未处理异常会取消其余任务，不适合直接用于“尽量保留 1–3 张结果”的语义。Python 官方协程文档 首版不按单图结果推百分比；真实采样 step 可保存诊断，但组 UI 只显示准备、等待、执行、不定加载。所有槽有确定终态后统一发布四图或 partial；实际收到的文件可以先落盘抗崩溃，尚在执行的组不逐张揭示 1/4 进度。

7.3 部分失败与重生

终态归并：4 ready→completed；1–3 ready 且其余确定 failed/cancelled→partial；0 ready 且全部确定终结→failed/cancelled；存在任何 unknown→结果待确认，不编造缺席槽失败原因。父 task execution status 与 placement status 独立。 首版 partial 只提供查看失败、使用已得素材、显式“重新生成一组 4 张”；新 task/group/key，retryOfGroupId 关联旧组，旧成功不复制/覆盖。UI 不称免费重试，也不暗示仅补缺席方向。 补失败槽延后；虽然 DDL 提前保留 attempt 表用于请求追踪，修复还需 attempt 接受版本、迟到结果隔离、单槽配额、合并终态与收费说明，不能只加一个按钮。当前每槽默认一个 attempt，不做自动质量重抽。

8. 外部请求不确定、取消与 exactly-once 边界

任务本地幂等 ≠ 第三方 exactly-once。provider 接收请求与本地写 externalRequestId 不共享事务：若接收后响应丢失或 worker 崩溃，上游可能已收费但本地不知道。自动 retry 会产生第二次真实调用。 派发前保存 dispatch intent/request hash；收到上游 ID 立即持久化；可透传幂等 key 的 Provider 使用相同 attempt key。HTTP 客户端对创建请求默认不开通用自动重试；可重试 GET/下载需明确不发起新生成。 重启处理：未曾进入 dispatching 的 queued 可重新领取；已 dispatching/running 先变 reconciling；有 query ID 查原任务，无 query 能力则 unknown/needs_user。只允许恢复确定性的本地文件校验/数据库落位，不借恢复重新调 LLM/生成模型。 超时分三类：服务端确认未接受→可安全重提同意图；明确生成失败→用户新尝试；接受结果未知→只查询/等待人工处置。不能按 elapsed 时间自行把 unknown 变 failed。真正要另起新创作需明确是新请求，不承诺避免旧请求费用。 取消先记 cancelRequestedAt；queued 且未派发可以确定 cancelled；已派发调用 Provider 能力，只有明确回应才显示停止已确认。不支持取消时停止后续步骤和自动落位关注，已生成资产保留；取消既不意味着退款，也不删除成功输出。 ComfyUI 全局 interrupt 等行为必须单独验证能否影响其他任务；多用户或共享 GPU 时不能假装它是精确 task cancel。切换 Provider 配置只影响新任务，运行任务持久 provider revision/模型参数并继续向原请求查询。

9. 蒙版坐标、版本、alpha 与显式提交

9.1 模式状态与输入

手动图下“抠图”只创建 MaskSession 并识别；Agent 对单图完整明确意图，经真实 LLM 计划与服务端校验后自动走同一个识别服务，至多一次自动识别。detecting→editing→saving_revision→applying→completed/apply_failed，识别失败独立 detect_failed；蒙版和透明图是不同 Asset.kind。 原图解码时一次性处理 EXIF orientation，记录归一化像素宽高；蒙版必须对应同一 sourceAsset 内容 hash、方向、宽高，禁止自动拉伸错误尺寸蒙版。普通图片允许 source alpha，透明输出仍保留它。 前端 pointer 经过 screenToWorld→对象逆变换→原图像素坐标；不支持旋转/翻转的首版把这些变换禁用。对当前等比图：px=(worldX-objectX)/objectW*sourceW，Y 同理；笔刷大小明确按世界/屏幕定义并映射，不能混用。 画笔/橡皮对原图尺度 mask 操作；快速移动使用相邻采样连线插值，pointer capture 保持笔画。显示层半透明高亮，“高亮区域将保留”；UI 棋盘格只表示透明，不能烘进导出文件。源图背景仍可见。 蒙版灰度 white=keep/black=remove；局部重绘 white=repaint 是另一种 semantic enum，接口/工具不能共用未标语义的 maskImage。初版辅助选择未验则不开放。

9.2 草稿、显式 apply 与像素算法

每个完整 stroke 进入蒙版 undo 栈，并写 IndexedDB 草稿；周期性 raster checkpoint + stroke 增量避免每次 pointermove 保存整幅 RGBA。跨刷新至少恢复最近已持久化栅格版本；不承诺还原全部本地 undo 历史。 服务端 MaskVersion 为 immutable PNG，hash 标识提交内容。PUT 相同 revision/hash 可重复成功，不同 hash 409；新 revision 必须基于 latest。mask 版本上传失败允许继续本地编辑，但 apply 不可被误认为已提交。 点击蒙版栏“抠图”冻结 revision，先等该版本保存 ACK，随后原子消费 continuation（若 Agent）并创建 apply Task；前端锁定本次编辑和重复提交，按钮“生成中…”，原图/蒙版叠层保留。聊天、退出、笔画、恢复不能触发该端点。 像素合成建议 Aout=round(Asource*M/255)；保留源 RGB，不把原透明像素恢复不透明。灰度 M 先按明确色彩规则转换，不能误把 RGB 的 red 通道当任何蒙版；尺寸、通道、最大像素数通过验证后在 Pillow 输出 PNG。 该 apply 是确定性合成，不需要再调用生成大模型。进程崩溃可以按同 task、相同输入 hash 继续确定性处理；成功输出以唯一 task/output 关联，不新增重复透明资产记录。合成质量仍需软边/发丝/半透明物体样本验收。 失败保留源 Asset、MaskVersion、error 和 taskId；“返回蒙版”只回 editing。用户未修改又重新点按钮属于明确的新 apply attempt，仍使用新的操作 key；网络未知则查旧 task，不能直接解锁新 apply。

9.3 退出、源图移动/删除与撤销

退出默认先保存草稿并返回普通选择，保存成功轻提示“草稿已保留”，不每次增加确认。只有保存失败才显示继续编辑/重试保存/明确放弃草稿；成功保存才称已保留。识别中退出可请求取消或停止关注；晚到 mask 只存 session，不自动重新打开编辑器或生成透明图。 源对象移动不改变 mask；完成落位读取源对象当前几何。源 asset 被替换则旧 session 不再直接 apply，提示重选/重新识别；仅对象缩放保留原 asset 时可继续，像素蒙版仍按原分辨率。 源对象删除采用 tombstone，任务输入 asset 不删。输出存资产并标 placement=needs_placement，消息“结果已生成，尚未加入画布”；用户手动加入后才可认为放置步骤完成。完成时若源对象已改用另一 asset 也采用此分支；禁止复活源图或把结果落到最近选中图片旁。 撤销结果插入写新的 compensation operation：移除该结果对象和本次布局影响，保留资产/任务，并记录 placement=reverted。若用户撤销了 pending 组占位，设置 suppression，迟到产物入库但不复活组；取消上游为独立尽力动作。 补偿布局依据当前顺序移除目标并重新排，而非覆盖一份旧全组 snapshot；避免撤销抠图结果时把后续用户缩放/移动也倒回。必要时 object revision 冲突暂停补偿并提示，不伪造成功。

10. 组布局、工具栏、文字与画板

固定 creativeSlots 0..3；displayOrder = 源图→较早派生→新派生→下一原方向，gap=24 世界单位；新结果追加在该源图派生链末尾。派生角色带 sourceSlotId，组完成仍显示“4/4 + N 个抠图结果”。重生是新组，不能把第五张变成新方向。 受控横排按显示对象真实宽度累加 x，纵向顶对齐；抠图源宽高与源图显示尺寸一致。组标题/边框可拖整组，单图仅选择/等比缩放；单图变化重算后续布局，首版不自由拖散或拆组。 源图保留位置；新派生在源图右侧派生链末尾插入，后续组员顺延。其他组/独立对象不自动移动；跨组碰撞给出定位/整理提示。重放布局带 layoutRevision，多个结果近同时到达由服务器事务串行排列，派生排序键用 apply task 持久创建时间及 ID 作为并列次序，不能用客户端收到事件时间。若较早任务晚返回，按既定顺序插回链内并顺延。更新 display_items 的排序在同一事务中重建该组序列，避免逐行改 sort_key 命中即时 UNIQUE 冲突。 画布新派生沿用源图显示尺寸，扩展组容器而不压缩原四候选矩形；对话四图预览只读 creativeSlots，抠图另建单图结果卡。不能将 CSS repeat(4,1fr) 改为 repeat(5,1fr) 后挤小所有图片冒充组内顺延。 单图选框贴边，四角圆点与边中胶囊、左上图片标签；控制点维持屏幕点击尺寸，所有点等比缩放，结束后写 width/height 并归一化 scale；不修改 asset 像素。组标题点击与图片/边框命中区明确分离。 DOM 工具栏按世界包围盒投影到屏幕，优先图下居中；左右 clamp 到排除顶栏、四工具、对话、输入框的安全矩形。下方不足先轻移视口，仍不足停靠画布安全区底部并显示对象名，文字/点击区不随画布缩小。 相机变化/ResizeObserver/选择变化在同一 rAF 批次更新；对象完全离屏隐藏跟随栏并保留定位入口。普通栏与蒙版栏互斥，点击栏不清选择；任务成功若用户在编辑其他对象则不夺焦点，仅通知可定位结果。蒙版栏右侧“抠图”按钮固定，左侧工具区横向滚动，主按钮不得卷出可视区。 文字用 Konva.Text 呈现，双击时 DOM textarea 同位置编辑；支持 composition/中文输入，Ctrl/Cmd+Enter 完成、Esc 恢复本次内容、空文本离开移除空对象。默认系统字体 32px，多行黑字，样式保存为纯数据。Konva 官方编辑示例 画板默认 1024×1024，在视口中心创建可命名空间框；不裁剪、不自动收养相交对象、不承诺合成导出。画布、文字、蒙版三套 undo/快捷键作用域，IME 期间不触发全局发送/删除；视频控件内部拖动不冒泡为画布拖动。

10.1 已确认的主题边界与原型实现

11. 真实 LLM 受限计划与可恢复 Agent

11.1 引用快照与 planner 输出

用户消息持久化 {documentId,objectId,assetId,assetHash,displayName,thumbnail}；选择 B 不改已发送 A；planner 只拿允许引用句柄 ref_1 与元数据，不直接枚举全库。首版一个引用；无引用/多引用应澄清，未接视觉模型不能说看到了服装、身份或图像细节。 一次消息仅一次模型规划，保存模型/提示词版本、结构结果、延迟和 provider requestId；不保存或展示模型隐藏思维。模板只可作加载/错误文案，不可替代真实 LLM plan 验收。格式无效明确失败，首版不自动多次纠正/重试。

{
 "type":"object","additionalProperties":false,
 "required":["decision","reference","steps","question"],
 "properties":{
  "decision":{"enum":["plan","clarify","unsupported"]},
  "reference":{"enum":["ref_1",null]},
  "question":{"type":["string","null"],"maxLength":300},
  "steps":{"type":"array","maxItems":3,"items":{"type":"object","additionalProperties":false,
   "required":["tool","reference"],"properties":{
    "tool":{"enum":["prepare_subject_mask","await_mask_submission","place_cutout_result"]},
    "reference":{"const":"ref_1"}
   }}}
 }
}

domain validator 再要求 decision=plan 时 steps 必须依次且恰好为上述三项；clarify/unsupported 时 steps 为空。示例 schema 面向单引用；实际服务端根据已发送引用构造句柄枚举，引用数不是 1 时禁止 decision=plan。JSON Schema 形状通过不代表安全计划；校验 document、引用有效、能力、run 状态、调用次数及来源句柄映射，不相信模型自填 ID。 计划卡显示“只处理此图、准备蒙版、由你确认、新增一张透明素材到右侧、原图保留”。仅一个有效显式引用且用户完整意图都在首例范围时，经服务端校验自动创建最多一次识别；不增加额外“准备蒙版”点击。混合超范围需求不能删去不支持部分后擅自执行，必须先澄清。 合法 plan、run/ToolCall 状态与唯一识别 Task 在同一事务落盘，避免重复计划事件/页面重连再次识别。模型/计划刷新不重跑；若准备完成时用户已切换到文字或另一蒙版模式，只显示“检查主体选区”入口，不抢焦点、当前选择或编辑模式。

11.2 工具白名单、暂停与 continuation

模型可提议的三个工具不是三个任意 API 权限：executor 固定顺序，只能对 run 的 ref_1；await_mask_submission 为持久挂起，place_cutout_result 只能消费前一步已生成输出。没有 shell、文件路径、任意 URL、删除资产、跨文档操作或背景生图工具。 识别完成事务写 MaskSession + MaskVersion + ToolCall completed + run awaiting_user + continuation。凭据由随机 continuation ID、过期时间和服务端 HMAC 签名构成，token hash 存库；服务可按持久记录重建同一凭据供当前画布客户端读取，避免仅存 hash 后无法恢复明文。绑定 run/session/action/source hash，建议有效 24 小时；签名密钥仅在服务端，token 不给 LLM、不进模型上下文或 SSE 广播。 过期 token 不重跑识别/模型；用户恢复同一等待状态，经引用复验、显式 renew POST 重新签发并撤销旧 token，普通 GET 不修改状态。apply 接收 {maskRevision,operationId,continuationToken}，一个事务检查 token active、session/source、run version，再 consume token 与创建 task。重复同 operation 返回原 task，不因 token 已 consumed 报错。 蒙版编辑可增加 revision，token 绑定 session/source 而不预先锁最初 revision；点击时服务端验证提交 revision 已存在且为此次当前确认版本。聊天“继续”只能返回定位蒙版的 UI action，不能调用 apply 或消费 token。 挂起不占 worker；刷新 GET run 返回原计划/步骤/待确认位置，无新模型调用。来源失效时 needs_user，不替换引用；另发新需求先结束未执行步骤形成新 run，不暗改已执行计划。 首例限制建议：同文档至多一个非终态 run；一次模型规划、最多一次自动识别尝试、一个用户确认后 apply、零文生图/视频调用、零自动质量重试。确定识别失败可用户显式重试并在 tool_attempts 记新 attempt/operation/task，原 ToolCall 保持同一步而不抹去失败历史；unknown 不重试；额度记录不与实际计费金额混淆。

3.2 发送后自动准备蒙版，还是再点一次准备？

初始产品/交互草案保留“准备蒙版”或执行入口。用户希望最多一个“准备主体选区”按钮。UI 主张范围卡只告知，发送明确需求后自动准备，以减少额外点击；最终透明生成仍只有蒙版栏“抠图”。

交互提出自动切换模式可能打断文字或另一个蒙版，不能偷偷把用户后来选中的 B 替换回 A。产品、交互与全栈直接讨论后达成条件：完整意图明确、一个显式引用、真实 LLM 有效计划、服务端能力与范围校验通过，事务建立唯一识别任务，自动最多一次；歧义及混合越界请求先澄清，零工具调用。后台就绪不抢焦点，显示“检查主体选区”。等待用户状态持久化，刷新不重新规划或识别。

用户第三轮读取回应后有条件接受自动准备，不再坚持默认准备按钮；接受条件为阶段与来源可见、不抢焦点、恢复不重做、最终仍由蒙版栏提交。本轮推荐据此删除默认额外准备按钮。

3.3 部分失败为何不只补失败方向？

交互建议先保留旧组，另生成完整四图组。全栈解释局部补生成增加槽位 attempt 版本、过期响应隔离、单槽替换、费用说明及供应商能力契约；整组重生依赖更少且不损失成功图。用户担心“重试”被理解为免费或只补两张。

收敛建议：按钮“另生成一组 4 张”，旁边说明旧组保留、新调用可能产生费用、内容可能不同；服务端新 key/new group，记录 retryOfGroupId，保留旧方向快照。未知结果只查询原任务；允许离开、浏览与手动编辑，不让无限等待阻断整个文档。

3.4 原图旁的多个派生结果如何排列？

UI 提出保持世界坐标尺寸，扩容与顺延，不能等分五列。交互提出按创建顺序追加，避免每次插入都改变已存在派生结果的相对顺序。主持早期草稿为最新在前、16 单位间距，此处根据质询明确修订。

收敛建议：源图 → 派生1 → 派生2 → 下一候选，24 世界单位间距；四个 creative slots 永不增加，display order 单独扩展。原图右邻是派生链；第一次结果紧邻源图，后续在该来源派生链尾追加。右侧四图预览仍是四候选，抠图另建有来源的结果卡。

3.5 退出蒙版是否每次确认？

用户提出默认保留草稿比每次弹出弃改对话更有把握。交互与产品接受：正常退出先真实保存草稿，成功后离开并提示；保存失败时才提供继续编辑、重试保存、放弃。全栈要求把本机草稿与服务端确认区分，不能以 sendBeacon 或内存中的草稿证明可靠保存。

本轮推荐默认保存退出；重复打开读取同一 MaskSession/MaskVersion，不重新识别。生成失败回蒙版也不自动 apply。最终按钮版本快照和幂等约束必须在服务端生效。

3.6 Python 迁移如何避免重写全部前端或同时写两套数据？

全栈建议继续使用已有 JS + Konva，将 Python 从当前 rembg 工具服务推进到领域 API 和独立 worker；SQLite 负责文档、任务、会话与事件，本地不可变文件存媒体。产品与交互要求新旧入口均能打开正确文档，后台完成不得覆盖用户修改。

收敛建议：契约与真实能力先行；副本迁移 dry-run；短暂停写并排空旧任务；校验 ID/hash/引用后切换；已迁移文档禁止旧 JSON API 写回。API 和 worker 共享同一 repository 规则，不能各自维护一份真相。新数据产生后，回滚不能简单覆盖旧备份。

建议： 首版只下载单个已生成/上传的原始资产：透明主体为 PNG，普通图片保留存储格式和像素尺寸，视频原文件；頂栏“导出”未选中可下载资产时提示先选中图片或视频。批量/画板合成留后续。画板默认 1024×1024 作为可命名空间框，支持位置/大小保存，首版不裁剪内容、不自动改变对象归属；界面文案明确“用于组织素材，暂不合成导出”。文字采用默认系统字体、黑色 24 px，多行纯文本，支持修改/移动，Esc 退出编辑而不是删除对象；精细排版后续。上述默认均为本轮建议，可由交互角色修正。

验收： 选择透明结果下载能获得带透明通道的 PNG；无对象时导出不进入假加载；浏览器发起下载只标“下载已发起”。画板和文字新增后刷新重开仍存在；点击取消本地文件选择、关闭资产面板均不新增对象。未实现的工具在评审原型中标“后续”，不能产生虚构的成功反馈。

两条 Agent 用例比较

用例用户任务与价值能力依赖验收难度与范围推荐
A：引用一张图，协作抠出主体并放在旁边用户用普通话指定动作；Agent 解析范围、准备可修改蒙版、等待用户决定主体边界，再完成透明素材落位。锻炼引用、结构化工具、暂停、任务与文档恢复明确资产引用、蒙版识别与编辑、透明合成、对象新增、持久化；无需宣称视觉语义理解低至中：一个源图、一份提交蒙版、一张派生素材；人工提交点清楚，易于故障注入首版推荐
B：抠出主体，再生成四个方向背景供挑选为下一步创作准备主体及背景候选，更显多步骤价值；不承诺自动合成成图A 全部＋四方向规划/生成；若“匹配原图风格”则还需已验证视觉理解或用户描述中至高：双生成阶段、两个独立结果组/派生关系、部分成功、继续执行与调用范围更复杂A 与四图单轮均验收后再做

A 的价值不在于多放一层聊天按钮，而在于将“你指的是哪张图、处理到哪一步、何时需要你调整、失败保留了什么”做成可追踪且可恢复的交互。若不能完成这些能力，暂不应把普通一键抠图包装为 Agent。

01-产品经理-第二轮质询

产品经理 · 第二轮质询与第三轮推荐

日期：2026-09-09。已读用户第二轮、UI 第二轮、全栈第二轮及主持 v0.4 PRD 草稿。本轮新增评审意见，不修改产品、既有报告或 PRD 草稿，不调用模型；没有把方案讨论当作实际验收或真实用户研究。

共同讨论对象仍是用例 A：显式引用一张图 → 有限计划与主体选区 → 用户在蒙版栏点击“抠图” → 透明素材紧邻原图落位。

1. 计划触发点：接受范围告知，去掉通用“执行方案”

用户异议： 用例 A 有条件成立，必须看清处理哪张图、会新增一张透明图和哪里需要人工确认；如有按钮，叫“准备主体选区”，不能连用确认方案、执行方案、继续执行。该角色尚未验证真实使用价值。

UI 异议： 首轮产品流程发送后准备蒙版，交互/主持稿另加“执行方案/准备蒙版”，制造重复点击；建议单图明确意图发送后自动准备，范围卡仅告知。

产品回应： 接受 UI 在用例 A 的有限范围内自动准备。用户已经显式引用并要求“把这张图主体抠出”，发送是对这一次准备动作的直接意图。范围卡不增加同义确认；它固定显示“处理：人物原图；先准备主体选区，由你确认；生成 1 张透明图片放在原图右边，原图保留”。最终结果仍由蒙版栏“抠图”提交，不能用发送、计划生成或聊天“继续”替代。

与交互角色实际讨论： 已通过消息讨论。交互最初支持一个“准备主体选区”按钮，理由是自然语言解释与模式切换存在风险；随后接受单图明确意图下自动准备，并提出不抢焦点、后台就绪后可点击“检查主体选区”的条件。产品接受这些条件。此项记录的是实际收到的回应，没有推断所有角色已同意。

推荐操作合同：

  1. 只有明确要求处理当前唯一有效引用，且 LLM 受限计划通过服务端校验后，才允许自动发起最多一次主体识别。
  2. 问“怎么抠图”、无引用、多引用、混合多个目标、引用失效、超能力范围均先澄清或说明不支持，不把不支持的部分删掉后偷偷执行其余部分。
  3. 范围卡与真实任务状态先保存并显示；不以固定模板伪造已经执行工具。
  4. 若用户仍在原图场景且无其他编辑，可进入对应蒙版模式；若用户已经编辑文字、选中 B 或进入其他蒙版，后台准备不覆盖当前状态、不抢焦点。对话显示“选区已就绪 · 检查主体选区”，点击才回到 A。
  5. 识别失败不自动连发。此时允许明确的“重新识别”；暂停恢复可以提供“检查主体选区/继续编辑”。这些是具体恢复动作，不是默认每轮多一个执行确认。
  6. 蒙版结果就绪持久化为 awaiting_user；刷新恢复同一次计划与草稿，不重新问模型、重新识别或自动生成透明图。

接受/保留状态： 产品接受 UI 的默认自动准备；交互已在上列限制内表示接受。全栈随后通过消息明确接受自动准备，要求接受后的计划与待执行识别任务事务内写入，防止重连重复识别；识别完成后持久化 awaiting_user，最终提交原子消费 continuation。其核心要求不依赖额外准备按钮。用户第二轮只明确支持一个具体准备按钮或减少重复确认，尚未收到其对自动准备合同的直接回应；不把未收到的回应写成全员共识。

2. Agent 不能只是抠图包装：接受全栈的独立验收门槛

全栈异议： 固定文案转抠图不足以验证 Agent，必须有真实 LLM 的受限结构化计划、引用/范围校验、暂停恢复及失败测试。

产品回应： 接受。这与首轮“可追踪、可恢复而非多一个聊天按钮”的价值判断一致。自动准备减少一次同义点击，不删去真实计划、校验器、ToolCall 记录与 continuation。产品验收应直接检查这些可观察行为：

情形期望用户体验必须证明的行为
明确一张引用＋抠出主体简短范围卡→识别→等待检查实际模型产生有效受限计划；只识别指定资产，最多一次
“这张图”但无引用 / 多引用要求先选择一张并显示当前引用禁止识别与结果调用，不能猜当前或最近资产
“抠图并生成背景/批量处理/改其他画布”解释首版可做的范围，等待用户改为单图用例不静默执行半个目标，不进入背景生成或跨文档操作
非法工具、路径、URL、资产版本或模型格式明确失败/要求更新引用，原图保留服务端拒绝无效参数，不能让模型任意取文件或执行工具
蒙版就绪后刷新回到“等待你检查主体范围”同 session、同蒙版版本，无新 LLM/识别/合成请求
聊天发送“继续”定位到蒙版和明确的“抠图”按钮聊天不能消费最终结果提交令牌

真实 LLM 起始意图集与 Mock 状态机验证分开报告。建议接受全栈的 20 条起始意图集作为实验规模，但不写已测通过、不设虚构有效计划比例。若仅 Mock 或前端关键词分支可运行，原型应标模拟；生产 Agent 用例仍待验收。

3. 部分失败：接受“另生成一组 4 张”，补齐时间与费用含义

用户异议： “重新生成”可能被理解为只补失败两张。全栈异议： 新组会再次调用四张，不能称免费重试或暗示复用成功图。

产品回应： 接受，按钮统一为 “另生成一组 4 张”。按钮旁就地说明：“原有结果保留；将重新生成四张，内容可能不同，并按所选服务产生新的调用与费用。”无法确定价格时不显示估算金额，不新增虚构积分体系。

此入口仅适用于已明确终结的失败/部分完成组。新组使用新的 operationId，记录原组关系，复用原需求与固定方向快照；修改需求则按新创作处理。原组仍显示 2/4、有效图和失败位置。计费不确定不代表必须再弹一层确认，动作名称和相邻说明必须在点击前可见。

验收： 点击一次出现新的四槽位组，旧两张仍在；不覆盖、不叫“补 2 张”，不自动触发。只补失败方向延后，取舍是开发与理解更简单，但时间/费用可能更高；该取舍必须保留在技术方案中。

4. 结果未知不等于被困住；草稿默认保留而非每次询问

用户异议： 未知只查询可以避免重复调用，但不能把用户困在等待页；退出草稿最好默认保留，真实保存后才提示。

产品回应： 接受，状态文案为“尚未确认结果”，保留最后已知状态及查询入口。允许“查询结果”“返回我的画布”，也允许查看/下载已有资产、平移画布、编辑文字等无关操作。服务无法对账时未知任务仍保留，不能因等得久或用户离开而转成失败或安全重试。

推荐首版同画布未知 Agent 执行仍占一个逻辑执行槽（不占 worker）；输入草稿可写，新的执行暂不发送，避免同一会话交错。用户可以离开或继续手动操作；若选择另一份画布则不会把原任务串过去。这一限制是产品/实现建议，不扩大为整个应用锁死。

蒙版退出合同： 笔画结束保存本机草稿并同步服务端；一般退出直接保留，在真正保存成功后给轻提示“选区草稿已保留”。若仅本机成功则写“草稿已保留在本机”；服务端确认后才可写“草稿已保存至服务端”。恢复时展示“已恢复上次调整”，并验证同源资产与版本。

  • 正常退出无放弃确认弹窗；“返回画布”“返回我的画布”不暗含删除草稿。
  • 明确“丢弃选区草稿”才删除；下一句聊天不自动提交旧草稿。
  • 若本机与服务端均保存失败，离开时提供“留在画布 / 重试保存 / 明确放弃”，说明刷新可能丢失本次调整；不得假报草稿已保留。
  • 生成提交冻结当前蒙版版本，已提交任务结果与继续编辑草稿分开；失败回到保留蒙版，不自动重试。

对主持草稿的修正建议： §6 当前“有改动时保留草稿退出/放弃/继续”容易变成每次退出都弹框，建议改为上述正常自动保留、失败才保护。此处为明确修订建议，不直接改既有文件。

5. 视频必须真实联通；派生排列建议统一

用户异议： “已经有视频对象”不是完整入口；用户需要知道视频在哪个画布、有没有使用自己的图片。

产品回应： 接受，首版完整路径为“已验证的文生视频入口 → 平台资产 → 导入资产 → 加入〔当前画布名〕 → 视频对象预览/原文件下载”。至少一条真实视频任务要贯通保存、导入、重开、播放、来源和下载验收。仅创建样例视频卡片不满足视频功能完成标准。

来源保留原任务、原提示词、输出资产与使用它的文档。文生视频显示“来自文字描述”；没有输入图就不展示参考图关系。已有历史视频缺来源数据时明确“来源未记录”，不能根据当前选择补造。关闭视频预览停止播放并恢复原对象焦点；图生视频/分镜/时间线仍后置。

UI 对派生排列提出的“候选 01 → 派生 1 → 派生 2 → 候选 02”与间距 24 世界单位，交互第二轮也支持，产品接受。理由是新增第二派生时不重新安排已有派生的相对顺序，更利于找回；原图位置与尺寸不变，组扩容，候选固定 01–04。主持草稿当前写最新最靠原图、16 单位，与上述建议冲突，应只留一份最终默认。此为本轮默认值建议，不影响用户已确认的右邻、原图保留和四方向数量。

第三轮最终推荐（供主持收敛）

  1. 采用用例 A，明确一图意图发送后自动准备，计划范围告知；用户切换场景后后台就绪不抢焦点；唯一透明结果提交仍在蒙版栏“抠图”。无/多引用、混合目标和无效引用先澄清，不部分执行。
  2. 用真实受限 LLM 计划、服务端校验、ToolCall 与持久 awaiting_user 验收 Agent；只做模板或 Mock 的交互文档不能声称生产 Agent 已完成。

5.3 幂等与恢复细节

  1. 客户端为一次用户意图生成 UUID operationId，存本地 pending operations。双击、响应丢失重试使用同一 ID。相同 ID 不同规范化 body 返回 409，不静默复用错误任务。明确点击“再生成一组”才新 ID。
  2. API 在一个事务内创建 Operation + Task + Group/Slot + document placeholder + message refs，提交后才返回 202。worker 领取任务通过原子状态更新与 lease；API 重启不导致同任务重复领取生效。
  3. worker 在网络提交前持久 dispatch intent；响应收到后立即保存 externalRequestId。崩溃落在两者之间是无法普遍消除的不确定窗口：如果上游有 idempotency key 则透传；否则先查询/人工恢复，不能承诺跨任意提供方 exactly-once。
  4. 结果按 Task/Slot/Attempt 落盘，四槽位达到终态后统一发布组结果；随后在事务中写 asset refs、文档对象变换、消息关联、事件。完成事件重复发送允许；唯一输出约束与版本检查防止重复插入。
  5. SSE 每条包含 sequence、documentId、entityVersion。连接先拿 snapshot + watermark，再从该水位补事件；事件保留期过了返回 reset-required 并重新读快照。快照必须能覆盖文档依赖任务，不能把“活动列表中没有”判成丢失。
  6. 前端以服务端文档为基线 + 未 ACK 本地命令重放；后台插入结果不会被旧全量快照覆盖。几何拖动可按 delta 对新基线重放，文字/重命名冲突保留双方内容并提示；不必引入 CRDT。
  7. 任务引用和结果组随文档长期保存；全局历史列表分页只用于浏览，不作为恢复真相。引用中的资产不会因“最近 500 张”裁剪被删除。移除画布对象仅移除引用，不立即删除原文件。
  8. 返回画布列表先 flush 已有编辑并等待对应 ACK；失败保留 IndexedDB 草稿与明确恢复入口。刷新恢复草稿要比对 revision。beforeunload/sendBeacon 只能尽力发送，不是保证已保存。
  9. 撤销是新的文档操作：移除结果对象不删除 task/asset；若撤销提交时任务仍运行，写 outputPlacementSuppressed 标记并发取消请求，迟到结果入素材库但不把用户删掉的对象复活。用户可手动重新放入。

六、四图同时生成的具体实现与难点

不能用已有 batchCount 改成 4 作为方案。 推荐 provider capability 明确表达：

{
  "textToImage": true,
  "creativeGroup": {
    "size": 4,
    "distinctPromptPerSlot": true,
    "dispatchMode": "native_multi_prompt_batch | parallel_requests | unsupported",
    "maxConcurrentRequests": 4,
    "realProgress": false,
    "recoverByExternalId": false,
    "verifiedAt": null

}

这些值只有验证后才能启用。单 API n=4 如果只能接收同一提示词，不能自动视为四方向；四个 Python 协程同时 HTTP 提交也不能证明上游 GPU 同时计算。产品“同时生成”的可验收含义建议是一个父任务统一调度，四个方向请求在同一个调度窗口全部发出，不等待任何方向完成后才发下一个；若用户要求严格 GPU 推理时间重叠，必须有原生多 prompt batch 或可观测的多个 worker，第三方黑盒不能直接承诺。

方向规划先从原提示词分出硬约束与可变轴，产生四个 {title,prompt,variationAxis,preservedConstraints}；检查主体、用途、明确禁止项未变化，四个方向不能仅改随机种子。首版可采用受控方向规划器；Agent 文本模型失败时展示规划失败，不能悄悄改变用户要求。方向规划次数也计入运行日志，实际模型费用/延迟需要单独测。

执行器为整组预留 4 个请求许可，避免占了 2 个再等待 2 个造成局部排队。容量不足时整个组排队；当该 Provider 最大能力不足 4 且无原生批量能力，返回 capability-unavailable。准备完成后并发创建四个执行协程，各自捕获异常并持久化 attempt；单槽失败不取消另外三槽。用 asyncio.gather(..., return_exceptions=True) 或在 TaskGroup 的每个子协程边界捕获异常；不能使用未处理异常会取消同组兄弟任务的行为。Python 官方并发语义

每张有效结果可先存服务器，但 UI 共同显示生成中，父任务全部终止后一起呈现 4/4 或 partial（1–3 张）。若超时尚不能确认某请求终止，状态是“结果待确认”，不是给缺席方向编失败原因。首版建议不补单个失败方向：保留 partial，用户可明确重新生成新的一组；若后续支持补缺失方向，它应是原组固定槽位的新 attempt，名称必须说明是补生成，不能伪称初次四方向任务。

需先测：provider 是否允许 4 请求、速率/并发限制、四种提示词差异、排队行为、取消与 requestId 查询、总时长与内存/费用；本轮未调用付费服务，以上都还是验收条件。

七、蒙版、画布与 Agent 的实现重点

7.1 蒙版的显式提交

  • 点击图下「抠图」创建 MaskSession，仅识别出灰度选区并叠加，背景原图始终可见。白=保留、黑=透明，中间灰度保留软边；与 inpaint 的“白=重绘”必须通过类型/字段区分，不能共用含糊的 mask 参数。
  • 画笔坐标先 screen→world→object local→原图像素。首版若不支持旋转，工具明确禁用旋转；若支持则必须用对象逆变换，不能仅按 x/y 除宽高。笔划按轨迹连续插值，避免快速拖动形成散点断裂。
  • 撤销/重做优先保存笔划命令 + 周期性栅格 checkpoint，不为每个 pointermove 保存整幅 4K RGBA；蒙版 session undo 栈和画布对象 undo 栈分开。蒙版位图存 IndexedDB 草稿、服务端保存版本，避免 data URL 塞入文档。
  • 点蒙版栏「抠图」时冻结 maskRevision，等待该版本持久化 ACK，创建有幂等 key 的 apply task。按钮和编辑一起禁用，蒙版叠层保留并显示不定进度；结果生成用本次版本，不重新识别。
  • 结果 alpha 建议 A_out = A_source × M / 255，防止对已有透明素材重新处理时恢复原透明像素。先统一 orientation、色彩通道和原像素尺寸，输出透明 PNG。当前 apply-mask 去除原 alpha 后直接覆盖，迁移时要加透明源图用例。
  • apply 失败返回相同 MaskVersion，用户回编辑再主动提交新 revision；响应不确定先查 operation/task。离开后任务仍可服务端完成；重开恢复 mask session 或最终结果。

7.2 组布局、控制点与视频/文字

生成组使用持久 display order，四原始槽位与派生对象的归属独立。抠图提交只预约来源关系；成功插入时读取源图当前位置和当前组 layoutRevision，原图不移动，抠图结果按 source → newest derived → older derived → next creative slot 顺序建议排列，同组后续 x 坐标按实际宽度+间距累计，容器宽度重新计算。重复抠图顺序为本轮建议，需要产品确认；跨组自动挪动容易扰乱用户排版，首版不自动推移其他组，只保持组内相邻并提供定位结果。

图片单选、组选择用不同 hit target：点图片选单图，点组标题/边框选组；拖标题移动整组，拖图建议首版按组内布局约束移动或仅调整大小，拆组后自由拖动的规则不要未经确定就实现。控制点视口尺寸固定，变换结束写 width/height 并重置 scale，保持资产原尺寸不变。

工具栏用 DOM overlay，位置用 worldToScreen 算图片底部中心；相对于画布可用矩形 clamp，避开左工具栏、右对话和底输入框；图片在底部则工具栏翻到上方，窄窗口栏内滚动。相机变化和 ResizeObserver 后同一 requestAnimationFrame 更新。蒙版栏替换普通栏，保存并恢复焦点。

文字以 Konva.Text 展示，进入编辑时使用定位在同处的原生 textarea，支持中文 IME；composition 时不触发全局 Enter/Escape/Delete。编辑完成只提交一次命令，Esc 回退本次文本。Konva 官方也采用 DOM 文本输入覆盖画布的方式。官方文字编辑示例

画板首版建议为可命名、可移动的背景容器，默认 1024×1024，暂不裁剪内容、不做合成导出；此默认尚未经负责人确认。视频在画布内展示海报帧和播放标识，单击选中/拖动，独立播放按钮或双击打开 DOM <video controls> 预览；不在大量 Konva 对象中持续逐帧刷新，也不增加时间线。

7.3 Agent 共用操作接口与首例建议

最小推荐用例：引用一张现有图片 → 说“把主体抠出来放旁边” → Agent 校验引用并准备蒙版 → 暂停到手动蒙版栏 → 用户调整并点「抠图」→ 服务完成透明结果并落位 → 对话提供结果和定位。它验证引用、工具、暂停、恢复、结果归属，又不以未确认的自动抠图跳过已确认步骤。四背景方向串联可作为下一例，前置依赖更多，首版不再承诺合成海报。

工具白名单建议 read_reference_metadata、prepare_subject_mask、await_mask_submission、query_task、locate_output；apply_cutout 只能由已经持久的用户显式提交事件驱动。Agent 不得到任意代码、shell、文件路径、任意 URL 访问或全局资产查询工具。若未接视觉模型，只说已引用该资产并调用主体识别，不能描述看到了具体内容。

每次 run 固化 documentId、引用 objectId/assetId/revision、工具数上限与允许的生成轮数；建议首例最多处理 1 个引用、1 次主体识别、1 次显式 apply，失败不自动重做已成功步骤。这里是产品运行范围设置，不新增账号/权限系统。模型输出只作为有结构的操作提议，经 server schema 校验与 capability registry 后才执行；手动入口与 Agent 调用同一 operation service。

新增指令在执行中保留为草稿，用户可中断当前 run 后再发送，或等待当前 run 完成；不暗中修改已经执行中的提示词、引用与 maskRevision。对话中“已完成”至少需 OutputRef 存在、文件验证通过、画布对象关联事务已提交，不能根据 LLM 文本自行宣告。

02-全栈开发-第二轮质询

② 全栈开发 · 第二轮具体质询与回应

日期：2026-09-09。已读产品经理、交互设计首轮与主持 v0.4 PRD 草稿。本轮是方案讨论，未运行真实模型或修改产品代码。第一轮证据见 全栈独立评审。

共同问题一：首条 Agent 会不会只是抠图按钮包装？

对产品的异议： 用例短本身不是问题，但“自然语言→固定文案→自动点抠图”不足以验证 Agent。必须让真实 LLM 输出受限结构化计划，并独立验收无引用、多引用、超范围意图、失效引用、模型格式错误与暂停恢复；否则不能将一键抠图改名为 Agent。

回应与最终推荐： 经产品/交互实际质询与主持确认，接受：显式引用一张图且完整意图明确→真实模型计划→服务端校验后自动准备一次蒙版→持久化 awaiting_user→用户在蒙版栏点“抠图”→PNG 和落位。删除中间草稿的额外“准备蒙版”点击；我的核心要求是真实计划、范围和暂停恢复，并不要求额外按钮。增加计划校验器、ToolCall 记录与单次消费的 continuation；无需为了表现“智能”加入背景、图像问答、搜索或自主反复尝试。

  • clarify、plan、unsupported 是模型输出的互斥类型；没有引用不能先调用识别工具。
  • 模型只选择服务端给出的引用句柄，例如 ref_1，不能自行传磁盘路径、URL 或另一个文档的 assetId。
  • 计划显示处理对象、最多一个识别任务、一个等待节点、一个透明结果；本用例图像生成轮次为 0。
  • 模型计划运行一次并持久保存；刷新不能自动再次调 LLM。格式校验失败本轮建议明确失败，用户可重试，不隐式循环纠错。
  • awaiting_user 不占 worker；浏览器恢复后继续同一个 session 和 mask revision。聊天“继续”只定位蒙版，不能获得 apply token 的消费权。
  • 仅一个有效显式引用且整个用户意图都在首例范围，才自动识别一次；歧义/混合越界先澄清，不删去不支持目标后部分执行。合法计划和唯一 detect task 事务落盘，重复计划事件或重连不二次识别；失败显式重试，unknown 只查。
  • 用户已经在编辑文字/另一蒙版时，后台准备不抢焦点与当前选择，只给“检查主体选区”入口；前端 mode epoch 只决定是否进入蒙版界面，不改后台任务事实。
  • 真实模型的 20 条起始意图集与 Mock 状态机测试分开。发布要求禁止工具调用场景零副作用；有效计划比例是目标，不是本次实测结果。

执行成本： 额外成本集中在一个受限 planner、引用句柄映射、持久暂停、错误视图和评估集；这些可直接复用到下一条多步工作流。相比直接把 rembg 当任意 tool 暴露，增加的是必要可控边界。

共同问题二：整组重生与补失败方向

对产品/交互的异议： “重新生成一组”更容易实现，但会重新产生四张，不能写成“免费重试”，不能暗示已有成功资产会参与/被复用。未知调用也不能因为用户等得久就转成普通重试。

回应： 接受首版“部分完成→旧组保留→显式新组 4 张”，新组记录 retryOfGroupId，使用新 operationId。复用原 prompt 和已固定方向快照；用户更改需求则作为全新创作组，不能假称同一次失败恢复。UI 文字明确“新建一组 4 张，保留已有结果”。

方案真实工程成本产品取舍
新组 4 张复用已实现的整组提交；新增父组引用即可；仍需新任务幂等保留旧组、契约清楚，但再次调用 4 张的时间/费用可能更高
仅补失败方向slot attempt 版本、多次终态、旧 attempt 晚到隔离、单槽容量/取消、组修复状态和原 prompt 追溯；需要精确解释收费与图像一致性少重复生成，但容易混淆“固定四图”和“补图”；首版延期合理

unknown 只允许查原 externalRequestId/operationId；只有证明上游未接受才能安全重发同一次未执行意图。无法查询时保留“结果待确认”，人工新创作也必须明确不是原请求的安全重试，不能承诺不重复计费。

共同问题三：Python 迁移与后台结果一致性

回应交互对唯一落位/撤回状态的要求： 同意，且由服务端实现。Task 的执行、Asset 的存在、Placement 的应用是三个状态；新增 placements 唯一 (taskId, outputIndex)，状态 pending/applied/suppressed/needs_placement/reverted。撤销写补偿记录，不能只在前端删对象。旧完成事件重新到达也不能覆写 reverted。

异议： 不能保留旧全量 JSON 保存作为新编辑器的常规写路径。即使有 SQLite task 表，旧 snapshot 仍会覆盖 worker 新插入的对象。单靠 BroadcastChannel 检测多标签页也挡不住同一页面与 worker 竞争。

推荐具体合同：

  1. 新 /api/v2 只有 Python 拥有文档/对象/资产/任务/会话；旧 Express JSON 数据只读迁移，切换时停旧文档写入口。旧生成实验入口临时保留时，只能向新资产域幂等导入，不直接写新文档。
  2. 前端发送 operationId + baseRevision + commands[]，SQLite BEGIN IMMEDIATE 后检验版本，应用文档修改、递增 revision、写 event/outbox，单事务提交。
  3. worker 落位使用相同 operation service。完成文件已入库但落位冲突时只重试数据库落位，绝不重新生成。
  4. 前端 GET snapshot 返回 eventCursor；以文档为范围从 cursor 接 SSE；增量事件按 entityVersion 去旧重放。历史缺席不代表失败，不能再依靠活动任务 snapshot 判丢失。
  5. 普通保存冲突返回 409 + currentRevision，保留本地草稿并重取基线；不以最后写入覆盖。单机 SQLite 不意味着 API/worker 同时写无需事务。
  6. outbox 保证业务数据与待通知事件在本地一起提交，SSE 游标保证可补发；它们都不能独立保证第三方模型 exactly-once。外部请求提交与结果记录之间存在不可跨库事务化的未知窗口。

向主持反馈的规范冲突

  • v0.4 草稿 A12 的“均不重复计费提交”应限定为“客户端重连/刷新/重复事件不产生新派发；上游未知时只对账”。第三方无幂等或查询能力时，不承诺普遍 exactly-once。
  • 原首轮全栈建议工具栏下方不足时翻到上方；本轮遵循主持/交互草稿，改为优先微移视口、必要时安全区底部停靠，保留图片下方规则。
  • 主持采用产品/交互第二轮统一：派生按创建时间追加源图派生链尾、间距 24 个世界单位；固定原候选矩形，扩组不缩卡。文字默认 32px；蒙版默认保存草稿退出，只有保存失败才出现保护选项。中间草稿的最新在前/间距 16 不再采用。
  • 一轮“同时生成”只能按可证据验收的定义承诺：原生四方向 batch 或同一窗口四路派发。不能从 4 个本地协程推断第三方 GPU 推理时间一定重叠。

同一个问题：引用一张候选图之后，如何在不中断空间关系的情况下完成抠图

质询一：产品经理提出单图 Agent 用例 A，交互稿又出现“执行方案”，是否重复确认

具体依据： 产品 A02–A04 是发送后准备蒙版，再等待用户；交互“引用对象与 Agent”流程多了“形成方案 → 执行方案”。两者如果不区分，会使首版流程变成“发送 → 执行方案 → 抠图”，其中中间按钮的作用不清。

UI 提问（已发送给主持，供产品与交互回应）： 在仅处理一个引用、仅准备蒙版的首版用例中，是否将计划卡作为范围告知，发送后自动准备蒙版，把产生透明结果的唯一确认点留在蒙版栏“抠图”？当目标、数量或能力超出该用例时才转成新方案，不能代用户扩大范围。

UI 方案： 采用 用户消息（含引用） → 范围卡（只处理该图，原图保留，新增 1 张透明素材） → 蒙版准备中 → 等待你确认主体范围 → 显式抠图 → 完成卡。计划卡不再加第二个同义主按钮。蒙版栏始终承担最终提交。此为待主持收敛建议，不声称产品与交互已同意。

可见验收： 从发送到蒙版就绪，画布上透明结果数量为 0；只准备/恢复/修改蒙版不会显示“已完成”。发出 A 引用后选择 B，卡片仍显示 A；如果资产已替换，卡片显示“引用已变化，请更新”，不能静默使用 B。

质询二：交互设计要求浮层落在安全区，如何保留“图下栏”和提交可达

具体依据： 交互首轮直接向 UI 追问 100% 缩放下四图横排与输入框冲突。v0.3 S39 实测工具栏宽 576px、内容宽 743px；尾部动作需滚动。S14 的 290px 栏当前能容纳，但添加笔刷大小与退出后会变长。

UI 回应： 支持屏幕坐标浮层，不用 transform 整体缩小按钮文字。按下列优先级处理：

  1. 由选中对象世界包围盒投影到中央画布屏幕区域，栏优先放在图片下方，间隙 12px；水平中心对齐该图片。
  2. 水平方向向安全区夹紧；安全区排除右侧对话、左侧工具和底部输入矩形。普通长栏内部可滚动，显示渐隐边/滚动提示，动作顺序不变。
  3. 蒙版栏拆为“退出固定区 / 可滚动工具区 / 抠图固定区”。“抠图”至少 72 × 40px，任何滚动位置都不能消失；有效蒙版之外一律禁用并显示原因。
  4. 下方高度不足时，在用户主动进入蒙版/定位对象的动作中可适度平移视口，让图下操作区进入可见范围。后台完成、用户正在文字输入时不自动抢视口。
  5. 仍无法容纳时，栏固定在底部输入上方的安全区，必须显示“蒙版编辑 · 候选 02”和“定位对象”。这是受限空间的例外收纳状态，需要在交互 PRD 单独展示；对象完全不可见时收起工具区，保留“定位选中对象”入口。

UI 提问（已发送给主持，供交互回应）： 是否接受该末级收纳态，且明确它不是新增页面，也不是工具栏任意跑到顶栏？默认图下形态仍是已确认要求，例外只解决几何不足。

可见验收： 1440、1280、1024px 宽度；25%、100%、200% 画布缩放；对象贴左/右/下边缘。普通栏与蒙版栏互斥；提交按钮、退出均可见；栏与输入框/对话无矩形交叠；浏览器焦点仍能到达当前栏；蒙版模式点其他图需按草稿保护规则退出。

质询三：四候选与派生素材能否从视觉和布局数据上都分开

具体依据： 产品 A06、交互“抠图与派生结果”均说原图保留、后续顺延、四方向编号仍 01–04。v0.3 S15 的五等分布局与这些规则相冲突。

已向全栈质询： 数据保存候选槽位与派生关系，布局保存原矩形；插入派生图扩容，不把 grid-template-columns: repeat(4, 1fr) 改成 repeat(5, 1fr)。对话中的原四图组预览仍是 2 × 2；派生抠图用单图结果卡，引用同一资产。

可见验收： 插入前后源图 x/y/宽高不变；新结果在源图右側；后一候选只向右移动；原始四槽 ID/顺序不变；刷新不重复插入；原图再次抠图的第二派生排在第一派生后。

质询四：保存、任务、模式的状态是否混为“完成”

具体依据： 产品 P0-3 区分模型完成与落位完成；交互要求文档保存、任务与蒙版草稿分别显示；UI 首轮另指出断连不等于任务失败。

UI 回应： 采用三层状态承载，不在每层复述所有状态：

状态层承载区域示例不可替代的事实

蒙版待确认/编辑中画笔、橡皮、撤销、重做有有效蒙版更新草稿；局部蒙版历史与画布操作历史分离Esc/退出保存草稿，恢复普通选择；不生成结果
蒙版就绪蒙版栏“抠图”非空有效蒙版、源版本有效、无本次提交在途固定当前蒙版版本与源版本，按钮生成中；锁定此次蒙版编辑与重复提交响应未知查询该次提交；不得直接再次调用
结果生成中收到有效资产并确认落位任务与对象归属一致源图右侧新增派生图；组内后续项顺延、容器扩展；恢复普通工具栏失败保留已提交蒙版与原图；“返回蒙版”不自动重试
有草稿再次进入同一源图抠图原资产版本相同显示“已恢复蒙版草稿”，可继续改或重新识别原资产已改变则标注旧草稿不可直接复用，显式重新识别

补充默认：

  • 蒙版画笔表示“保留区域”，橡皮表示“移除选区”，提供可调笔刷大小；辅助选择未有能力依据时禁用并说明，不假装可用。不得用不透明蒙版完全遮住源图细节。
  • 点击其他图片、开导入面板或返回均先退出蒙版并保留草稿；若草稿持久化失败，提示留在编辑/明确丢弃草稿，不能静默丢失。应用刷新恢复草稿但不自动进入生成。
  • 结果位置由落位时源对象位置计算；源图在生成过程中移动，结果跟随源图的最新位置。建议派生图依创建顺序紧随源图排列：原图 → 派生 1 → 派生 2 → 下一原方向；四方向编号始终为 01–04。
  • 组内水平间距固定为建议值 24 个画布单位；对其他独立组的冲突先明确显示结果及“定位结果”，不在首版自动搬动无关对象。跨组自动避让属于后续能力。
  • 源图在生成中被移除时，完成资产保留在本画布会话/资产中，提示“来源对象已移除，结果尚未放入画布”，提供显式加入；不复活源对象。Agent 将此视作“结果已生成、放置未完成”，不能显示全部完成。
  • 成功时仅在用户仍停留该次操作且未更换选择时选中新结果；用户正在编辑其他对象时保留焦点，以结果卡和定位操作通知，避免打断文字或蒙版操作。

浮层与按钮

  • 普通操作栏与蒙版栏互斥。工具栏基于选中对象屏幕包围盒定位，默认下方居中，保留间距；滚轮缩放只改变对象几何，不缩小工具栏文字/点击区。
  • 可用区域排除顶栏、左工具、右对话与底部输入框。横向越界向可用区域内夹紧，长栏内部横向滚动。下方空间不足时优先微调视口使图下工具栏可见；仍不足则将栏固定在画布安全区底部并显示“图片工具/蒙版工具”，不盖住输入框，不瞬间跑到无关联角落。
  • 选中对象完全离开视口时隐藏跟随工具栏，保留可访问的“定位选中对象”。点击工具栏按钮不清掉对象选择；在工具栏与对象间移动指针不关闭工具栏。
  • 图下“抠图”在单张有效图片且能力可用时可用；蒙版栏“抠图”只在有效蒙版且无提交在途时可用。两个同名按钮的辅助说明分别为“编辑主体蒙版”“根据当前蒙版生成透明图片”。
  • 下载仅对可读的完成资产可用，透明结果建议提供原始 PNG；不把浏览器已发起下载标为文件已存到用户磁盘。画板合成/全画布导出若未实现则不放可点击假入口。
  • 执行方案：计划完成、引用有效、能力可用、无冲突执行时可用。重试：确认终态失败且步骤可重试时可用。未知状态只可查询；不以短超时直接解锁重试。
  • 灰显按钮必须带能聚焦到的说明或相邻说明，不能只有颜色差异。未验证能力统一标“待接入/待验证”，不出现成功演示。

焦点与可访问性

  • 工具栏是真实 button；组/对象有名称；状态通过 aria-live="polite" 只播报关键变化，不每秒播报加载。图像方向使用“方向 1–4”，抠图结果使用“方向 1 的抠图结果”。
  • Tab 依次进入顶栏、左工具、画布可操作对象/组、底部输入和右侧对话。工具栏内部可用方向键切换；大画布提供对象列表或可聚焦对象入口，避免键盘只能操作周边面板。
  • 弹层打开后焦点进入其标题/首个操作，关闭回到触发按钮；模态预览约束焦点且背景不可操作。非模态对象工具栏不锁焦点。
  • Enter 在底部多行输入中默认换行，Ctrl/Cmd + Enter 发送；若产品最终改为 Enter 发送，必须考虑输入法组合态与 Shift + Enter，并在输入框给出快捷键提示。文本组合过程中不触发发送或全局快捷键。
  • Esc 的范围按最内层优先：关闭菜单 → 关闭预览/弹层 → 退出文字/蒙版模式 → 取消选择。Ctrl/Cmd + Z 在文字编辑、蒙版、画布三种作用域互不串用。

恢复和撤销的边界默认

  1. 画布撤销只撤销文档变更。 移动、缩放、插入、移除、文字编辑形成可逆操作；撤销已完成生成结果的插入时，资产与任务历史保留，且服务端记录已撤回的落位，刷新不能复活。撤销不把已执行模型调用“倒回去”。
  2. 已提交生成与画布保存独立。 生成请求必须先固定文档归属；后台完成由服务端持久化资产与文档落位，前端关闭也不能丢结果。UI 只有在对象确实持久化进入画布后把整项操作标为完成。
  3. 草稿分别持久化。 对话文本/引用、蒙版草稿可本地备份，画布服务端保存是“已保存”的依据。恢复草稿时显示来源和恢复状态；本地备份不等于全应用离线可用。
  4. 保存冲突不能悄悄覆盖。 多标签页或后台结果写入导致版本变化时，保留当前操作并重新获取最新文档；可安全重放位置/文字等操作后再保存，不能用全量旧快照覆盖新结果。
  5. 放弃未保存修改的范围写清。 仅放弃尚未持久化的名称/布局/文字变更；已经确认提交的生成仍继续；未提交蒙版/对话草稿默认保留，若要删除需单独明示。
  6. 能力不可用不扩大到全部编辑。 Agent 离线保留手动工具；某图像服务失效不清空文档；全应用服务离线只承诺已有内存/已缓存内容，不能把未开发的离线产品能力写成已完成。

第二轮希望其他角色回答的具体质询

  • 产品经理：是否同意部分完成首版采用“保留原组 + 显式重开四图组”，把补缺方向与自由拆组后置？这能避免“首版固定四张”与局部重试的歧义。
  • 全栈：是否能在服务端持久化唯一落位记录/撤回状态，并把“任务已结束、资产已生成、对象已加入”分开？否则刷新及撤销验收无法保证。
  • UI：长工具栏在 100% 缩放下遇到 4 张横排及底部输入框，能否给出安全区收纳状态，明确绑定哪张图，并保留用户要求的图下栏形态？
  • 用户角色：在蒙版退出后提示“草稿已保留”，再次进入恢复，比每次弹弃改确认是否更符合继续创作预期？需要明确这仍是基于假设的走查。
  • 所有角色：Agent 若选择“抠主体 → 生四个背景”的首条用例，是否接受蒙版处明确暂停，让用户点“抠图”后再继续已展示的其余步骤？本轮不应通过自动生成绕过该检查点。

待验证事项

  • 四方向的真实并发提交能力、整组终态定义、可取消程度和异常部分返回信息。
  • 蒙版识别与结果生成能否真正分离，源图/蒙版的尺寸映射和透明输出质量；笔刷图形不等于真实可用蒙版。
  • Agent 能否按可见引用正确理解图像；在视觉能力未验证前只允许使用指定资产的已知元数据及确定性工具。
  • 服务端持久化、重放、去重、撤销与后台完成的竞态处理，以及本地草稿恢复支持。
  • 视频已验证范围是文生视频流程；画布视频导入、预览/拖动、源素材关联和图生视频需要分别验收。

⑤ 交互设计 · 第二轮质询与第三轮推荐

1. 同一问题：发送单图抠图需求后，是否再点击准备主体选区

各方起点

角色原观点具体理由
交互首轮方案展示后显式执行需要看清实际引用、工具范围和结果数量；不能把任意自然语言自动扩大成工具执行
用户第二轮一个“准备主体选区”按钮，避免再叠确认/执行/继续希望普通语言解释下一步，不希望多次同义确认；最终仍在蒙版栏点击“抠图”
UI 第二轮发送后自动准备，范围卡只告知在单图、单能力的短流程中，中间“执行方案”增加无意义点击；保留最后的明确结果提交
产品经理直接回应有效单图、明确意图、真实 LLM 计划通过校验后最多一次识别用户发送已表达处理意图；歧义/超范围先澄清，不调用工具；透明结果仍只有一次显式提交

交互异议与直接回应

我最初向产品经理提出保留一个具体“准备主体选区”，删除泛化“执行方案”。担心的不是抽象权限，而是LLM 尚未解释完需求时，系统并不知道要执行哪个有限范围；自动准备还可能把用户从正在编辑的其他对象强行拉走。

产品经理回应建议采用 UI 方案，但以前置计划校验限制意图、引用、工具和次数。我接受这一取舍：在首条用例 A 的边界内，用户的明确发送意图足够触发识别，不必再加重复确认。我的原异议改由以下状态规则处理，而不是通过所有情况一律多一个按钮处理。

最终推荐（本轮建议）：

显式引用一张图 + 明确抠图意图 → 发送
  → 真实 LLM 产生受限计划 → 服务端校验
    → 有效且仅用例 A 范围：显示范围卡，自动准备最多一次主体选区
    → 歧义 / 多引用 / 扩大目标：澄清，不执行识别
    → 无效计划 / 失效引用 / 能力不可用：明确失败或不可用，保留消息
准备完成 → 持久化等待用户状态
  → 当前上下文适合：显示该图蒙版
  → 用户已在别处编辑：卡片显示“选区已就绪 · 检查主体选区”，保留当前焦点
检查/调整 → 仅点击蒙版栏“抠图” → 生成透明图片 → 持久化并落位 → 完成
  • 范围卡一句话即可：“处理「候选 02」；请你检查高亮保留区域；生成 1 张透明图片，放在原图右边，原图保留。”不要把内部工具名、continuation 或 schema 直接放进主流程。
  • 自动准备发生在计划通过校验之后，不能“边规划边先识别”。若用户同时请求抠图、改背景和生成海报，不能静默删掉后两项并开始第一项，应说明首版可完成的范围并澄清。
  • 只允许该计划的一次初始识别。识别失败不自动重试；用户点击“重新识别”创建明确的新尝试，未知识别状态只查原请求。
  • 自动准备可以在后台进行；自动打开蒙版必须确保用户仍在同一文档、未切换选择、未开始文字编辑/另一蒙版/拖动。用户先发送 A 后选 B，不将当前选中 B 偷换为 A。提示中的“检查主体选区”是恢复/定位入口，不是再运行一次识别。
  • “准备主体选区”保留为需要明确范围调整后的动作或保守替代方案，不再是默认短路径上的额外按钮。“执行方案”“确认方案”“继续执行”不连续叠加。
  • 聊天里输入“继续”、刷新恢复、重新打开选区均不能消费最终生成动作。只有蒙版栏“抠图”可以提交透明结果。

保留的分歧与取舍

用户角色明确提出一个具体准备按钮，UI 与产品倾向自动准备；交互在上述条件下接受自动准备。用户角色尚未在本轮对修订作再次回应，因此不能记录为“五方一致赞成取消准备按钮”。

两种方案都保留既有最终“抠图”约束。自动准备减少一次点击，适合本轮单图明确意图；显式准备对多目标计划更容易解释范围，但可能让非常短的任务变慢。推荐首版自动准备，未来扩展多步/多能力时重新评估具体动作确认，不能把本次结论扩张为 Agent 可以无界自动执行。

产品经理随后直接确认接受全部新增条件：后台就绪不得抢焦点，检查选区入口只恢复场景，歧义/混合超范围先澄清，失败不自动重试。本文据此将这些条件记录为产品与交互之间实际达成的共识。

3. 对 UI 第二轮异议的回应

浮层：接受末级停靠，固定退出与抠图按钮

接受 UI 的具体优先级，补入操作规则：

  1. 正常状态图片下方居中，图与栏间隔建议 12 屏幕像素；横向在中央画布安全区夹紧。
  2. 普通长工具栏可内部滚动；蒙版栏采用“退出固定区 / 可滚动工具区 / 抠图固定区”。最终“抠图”在任何滚动位置均可见，不让唯一提交入口滚走。
  3. 用户主动进入蒙版或点击定位时可以微移视口腾空间；后台完成和用户输入期间不主动移动视口。
  4. 下方仍无法容纳时允许停靠在输入框上方的安全区，显示源图缩略图或身份文字，例如“主体选区 · 候选 02”，并有“定位对象”。这属于同一编辑模式的例外布局，不是新增页面。
  5. 对象完全不可见时隐藏笔刷工具区，只保留身份与定位；回到对象后恢复完整工具栏。不能允许用户看不见目标仍误以为在给另一张图涂抹。
  6. Esc 先关闭栏内菜单，再退出蒙版并保留草稿。停靠布局切换不重建编辑会话，不清除草稿和撤销历史；焦点留在原有可用控件。

“抠图”固定区建议至少 72×40px，退出也保持可见。几何检查覆盖 1440/1280/1024px 窗宽、25%/100%/200% 缩放以及对象贴边。不得靠缩小整条工具栏使按钮可点击区域变小。

派生插入：固定原矩形，容器扩容

UI 报告了 v0.3 S15 的实际问题：插入第五个显示卡后，候选宽度由约 127px 变为 100px。这是 UI 的观测，本角色转引其结果。该表现与“原图保留、后续顺延”冲突，应作为材料及后续实现的明确修正项。

推荐统一默认：24 个世界坐标单位。 用于同组候选与派生项的相邻间距；不是屏幕像素。首轮交互与第二轮 UI 已使用 24，留出贴边选框及来源标签的辨识空间。主持草稿的 16 也可成立，但同一规格必须只保留一个默认。本轮推荐 24，具体值是设计建议，不是用户确认约束。

默认布局规则：

  • 保存每个现有对象的 x/y/宽高；新增派生图不能修改源图或其他原候选的宽高。
  • 派生图按源图显示高度等比展示，保留真实资产尺寸；不改变源图分辨率和比例。
  • 顺序推荐 源图 → 派生 1 → 派生 2 → 下一候选，按派生创建顺序追加。组宽度增长，后续候选仅水平顺延；对话中的原四候选继续 2×2 预览，派生另用单图结果卡。
  • v0.4 当前“最新派生最靠近源图”能让最新结果更近，但会不断挪动此前的派生结果。推荐改为创建顺序，结合新结果选中/定位减少寻找成本，使已存在布局更稳定。若主持保留最新优先，需明确这是尚有取舍的建议值，并同步所有文件。
  • 四方向 slot 永远只有 01–04，派生名称如“候选 01 · 抠图 2”；组摘要显示“创意候选 4/4 · 派生素材 2”，不出现 6/4。

可观察验收：插入前后原图 x/y/宽高一致，原候选宽高一致；新结果位置满足右邻顺序与 24 单位间距；组宽度增长，原候选顺序不变；刷新不再次插入；撤销只撤回这次派生及其造成的布局变更。

产品经理已直接回应接受统一 24 世界单位与派生按创建顺序追加；这与 UI 第二轮建议一致。主持仍需同步 PRD/技术方案中的旧 16 单位及最新优先表述，不能只在评审纪要改值。
