## 三、推荐架构及迁移路径

### 3.1 首版目标结构（本轮建议）

```text
原生 HTML/CSS/JS + Konva + DOM 工具栏/文字输入/对话
              │ JSON REST；按文档订阅 SSE
              ▼
Python FastAPI API
  documents / assets / operations / tasks / conversations / capability registry
              │
              ├─ SQLite：文档修订、操作、任务、组、消息、事件、资产索引
              ├─ 本地文件：immutable 原文件、缩略图、蒙版版本
              └─ 独立 Python Worker：持久任务轮询、Provider IO、工具调度
                       ├─ cloud/comfyui Adapter
                       └─ rembg 推理进程 / Pillow 像素合成
```

推荐 FastAPI 承担 Python API，以 Pydantic 校验明确实体与工具输入，前后端由同一 OpenAPI 契约生成/核对类型。保留原生 JS + Konva 是控制此次改造成本的选择；React 迁移不是完成这条产品闭环的前置条件。

生成任务要先持久化，再由独立 worker 执行，不能把 API 进程的后台回调当作重启可恢复队列。FastAPI 官方将 BackgroundTasks 定位为响应后的小型工作，重计算需要考虑独立工具；本项目先用单 worker + 数据库任务表即可，暂不引入 Celery/Redis。[官方说明](https://fastapi.tiangolo.com/tutorial/background-tasks/)

SQLite WAL 适合当前单机本人和体验者范围，采用短事务、busy timeout 与独立连接；同一时刻仍只有一个写者，不能跨机器共享 WAL 文件。图片推理、网络等待不占用数据库事务。出现多机器 worker、写冲突或并发用户需求时，再迁移 PostgreSQL 和队列。[SQLite 官方 WAL 约束](https://www.sqlite.org/wal.html)

### 3.2 Python 过渡：领域单一所有者，不双写

1. **冻结协议与样本**：记录当前 API 请求/响应和错误 fixture，不包含密钥；确定 schemaVersion。生成任务不得在旧/新系统中影子双跑。
2. **利用已有 Python 基础**：将 rembg `/v1/masks` 纳入 Python 服务工程，保持独立推理隔离。建立 `/api/v2` 文档、资产、operation/task 接口；Express 暂时提供旧界面和旧 API。
3. **迁移文档和资产**：先做只读 dry-run，统计文件数、文档数、引用缺失、ID 映射；新数据库写到新路径。真正迁移时短暂禁止文档写入并排空旧任务，备份旧数据，按旧 ID 导入；验证对象顺序、来源、文件 hash、可读性。未通过则继续旧服务。
4. **切换新画布**：新画布只访问 Python 所有的 v2 领域数据；旧 Express 生成入口可暂留，但输出经适配导入资产库，不能直接修改新文档。对外一个 origin，由 Express 暂代理或由前端统一指向入口，避免两个服务互相存画布。
5. **迁移 Provider 与任务**：先 Mock 与本地 fake HTTP，后迁移一个已验证真实图像 Provider；四方向合约独立验收。已有运行任务留在旧执行器排空，禁止按同 jobId 在两边执行。
6. **迁移完成条件**：工作台、文档、资产、任务、Agent 均由 Python 单一拥有，Express 仅在旧页面适配需要时暂留；经过同一组契约回归后移除旧 API。回滚必须考虑切换后的新文档：不能直接覆盖成旧备份；停写、导出增量或仅回滚流量到可读兼容层。

必要替代方案：若短期只要求“后端包含 Python”，维持 Express + Python 工具服务成本最低，但 Agent/任务/文档仍归 Node，不构成 Python 核心后端迁移。本轮推荐渐进迁移到 Python 领域核心；不要求一次性重写旧主界面与全部 Provider。

## 五、核心数据模型与一致性

### 5.1 建议实体

```text
CanvasDocument(id, name, schemaVersion, revision, updatedAt, coverAssetId?)
CanvasObject(id, documentId, type, assetId?, x,y,w,h, zIndex,
             groupId?, sourceObjectId?, createdByOperationId, deletedAt?)
  type = image | video | frame | text | placeholder | error
  text = {content,fontFamily,fontSize,color,align}; frame = {name,background}
Asset(id, kind, contentHash, mime, width,height,duration?, storageKey,
      sourceAssetId?, createdByTaskId?, originalMetadata, status)
ResultGroup(id, documentId, taskId, prompt, constraints, status,
            creativeSlotIds[4], displayObjectIds[], layoutRevision)
GenerationSlot(id, groupId, directionIndex:0..3, directionTitle,
               directionPrompt, constraints, seed, status, acceptedAssetId?)
GenerationAttempt(id, slotId, attemptNo, providerSnapshot,
                  externalRequestId?, dispatchState, error?, timing)
Task(id, documentId, operationId, type, status, progress?, stage,
     providerSnapshot, inputRefs, resultRefs, cancelRequestedAt?, version)
MaskSession(id, documentId, sourceObjectId, sourceAssetId,
            sourceGeometryRevision, status, latestMaskRevision)
MaskVersion(id, sessionId, revision, assetId, sha256, width,height)
Conversation(id, documentId); Message(id, conversationId, role, text,
                                    references[], groupId?, taskId?, runId?)
AgentRun(id, documentId, conversationId, sourceMessageId, status, limits)
ToolCall(id, runId, stepIndex, toolName, validatedInput, status,
         operationId, outputRefs[], error?)
Operation(id, documentId?, idempotencyKey, canonicalBodyHash, type,
          status, resultResourceId, expectedRevision, acknowledgedRevision)
Event(sequence, documentId, entityType, entityId, entityVersion, type, payload)
```

`creativeSlotIds` 永远四个；`displayObjectIds` 可包含抠图派生，因此“4/4 创意候选 + 1 个抠图结果”不会混成五个文生图方向。资产是 immutable 文件，对象是放在某张画布上的位置；同一 asset 可以出现在多个画布和消息中。

最低约束：`UNIQUE(scope,idempotencyKey)`、`UNIQUE(groupId,directionIndex)`、`UNIQUE(operationId,outputIndex)`、`UNIQUE(slotId,attemptNo)`、object/asset/task/message 的外键或等价应用校验；documentId、groupId 不能由客户端跨文档随意组合。资产文件先临时写入并校验后原子更名，再事务写索引及输出关联；崩溃后未引用文件由后台清理，不把半截文件标为 ready。

### 5.2 任务与蒙版状态

| 领域 | 状态路径 | 关键语义 |
| --- | --- | --- |
| 图像父任务 | accepted → preparing_directions → queued → dispatching → running → completed / partial / failed | preparing 期间只是规划；queued 时四个槽位共同等待；只有真实开始执行后才能写“同时生成”。不把规划和外部排队伪装成已在推理 |
| 外部请求不确定 | dispatching/running → unknown → reconciling → running / completed / partial / failed / needs_user | 超时或进程崩溃不等于模型未收到；查 externalRequestId。提供方不支持查询且提交结果不确定时，保留原任务并提示用户决定是否新尝试，不自动付费重发 |
| 取消 | queued → cancelled；running → cancelling → cancelled / completed / partial | `cancelRequested` 与“上游已停止”分开。无法取消时只阻止后续步骤，保留实际返回产物；不先谎报取消成功 |
| 蒙版 | detecting → editing → saving_revision → ready_to_apply → applying → completed / apply_failed | 只有显式「抠图」允许进入 applying；识别失败回 detect_failed；返回编辑不生成；退出保留草稿后回普通选中态 |
| Agent | planning → awaiting_user / executing → completed / partial / failed / cancelled | 等待用户抠图确认是显式挂起点，不占 worker；回复流结束不是任务完成 |
| 保存 | clean → dirty → saving → clean / dirty / conflict / error | ACK 只覆盖对应 local revision；保存请求中出现新变更，旧 ACK 后仍显示保存中/未保存 |

### 5.3 幂等与恢复细节

1. 客户端为一次用户意图生成 UUID operationId，存本地 pending operations。双击、响应丢失重试使用同一 ID。相同 ID 不同规范化 body 返回 409，不静默复用错误任务。明确点击“再生成一组”才新 ID。
2. API 在一个事务内创建 Operation + Task + Group/Slot + document placeholder + message refs，提交后才返回 202。worker 领取任务通过原子状态更新与 lease；API 重启不导致同任务重复领取生效。
3. worker 在网络提交前持久 dispatch intent；响应收到后立即保存 externalRequestId。崩溃落在两者之间是无法普遍消除的不确定窗口：如果上游有 idempotency key 则透传；否则先查询/人工恢复，不能承诺跨任意提供方 exactly-once。
4. 结果按 Task/Slot/Attempt 落盘，四槽位达到终态后统一发布组结果；随后在事务中写 asset refs、文档对象变换、消息关联、事件。完成事件重复发送允许；唯一输出约束与版本检查防止重复插入。
5. SSE 每条包含 sequence、documentId、entityVersion。连接先拿 snapshot + watermark，再从该水位补事件；事件保留期过了返回 reset-required 并重新读快照。快照必须能覆盖文档依赖任务，不能把“活动列表中没有”判成丢失。
6. 前端以服务端文档为基线 + 未 ACK 本地命令重放；后台插入结果不会被旧全量快照覆盖。几何拖动可按 delta 对新基线重放，文字/重命名冲突保留双方内容并提示；不必引入 CRDT。
7. 任务引用和结果组随文档长期保存；全局历史列表分页只用于浏览，不作为恢复真相。引用中的资产不会因“最近 500 张”裁剪被删除。移除画布对象仅移除引用，不立即删除原文件。
8. 返回画布列表先 flush 已有编辑并等待对应 ACK；失败保留 IndexedDB 草稿与明确恢复入口。刷新恢复草稿要比对 revision。beforeunload/sendBeacon 只能尽力发送，不是保证已保存。
9. 撤销是新的文档操作：移除结果对象不删除 task/asset；若撤销提交时任务仍运行，写 outputPlacementSuppressed 标记并发取消请求，迟到结果入素材库但不把用户删掉的对象复活。用户可手动重新放入。

## 六、四图同时生成的具体实现与难点

**不能用已有 batchCount 改成 4 作为方案。** 推荐 provider capability 明确表达：

```json
{
  "textToImage": true,
  "creativeGroup": {
    "size": 4,
    "distinctPromptPerSlot": true,
    "dispatchMode": "native_multi_prompt_batch | parallel_requests | unsupported",
    "maxConcurrentRequests": 4,
    "realProgress": false,
    "recoverByExternalId": false,
    "verifiedAt": null
  }
}
```

这些值只有验证后才能启用。单 API `n=4` 如果只能接收同一提示词，不能自动视为四方向；四个 Python 协程同时 HTTP 提交也不能证明上游 GPU 同时计算。产品“同时生成”的可验收含义建议是**一个父任务统一调度，四个方向请求在同一个调度窗口全部发出，不等待任何方向完成后才发下一个**；若用户要求严格 GPU 推理时间重叠，必须有原生多 prompt batch 或可观测的多个 worker，第三方黑盒不能直接承诺。

方向规划先从原提示词分出硬约束与可变轴，产生四个 `{title,prompt,variationAxis,preservedConstraints}`；检查主体、用途、明确禁止项未变化，四个方向不能仅改随机种子。首版可采用受控方向规划器；Agent 文本模型失败时展示规划失败，不能悄悄改变用户要求。方向规划次数也计入运行日志，实际模型费用/延迟需要单独测。

执行器为整组预留 4 个请求许可，避免占了 2 个再等待 2 个造成局部排队。容量不足时整个组排队；当该 Provider 最大能力不足 4 且无原生批量能力，返回 capability-unavailable。准备完成后并发创建四个执行协程，各自捕获异常并持久化 attempt；单槽失败不取消另外三槽。用 `asyncio.gather(..., return_exceptions=True)` 或在 TaskGroup 的每个子协程边界捕获异常；不能使用未处理异常会取消同组兄弟任务的行为。[Python 官方并发语义](https://docs.python.org/3/library/asyncio-task.html)

每张有效结果可先存服务器，但 UI 共同显示生成中，父任务全部终止后一起呈现 4/4 或 partial（1–3 张）。若超时尚不能确认某请求终止，状态是“结果待确认”，不是给缺席方向编失败原因。首版建议不补单个失败方向：保留 partial，用户可明确重新生成新的一组；若后续支持补缺失方向，它应是原组固定槽位的新 attempt，名称必须说明是补生成，不能伪称初次四方向任务。

需先测：provider 是否允许 4 请求、速率/并发限制、四种提示词差异、排队行为、取消与 requestId 查询、总时长与内存/费用；本轮未调用付费服务，以上都还是验收条件。

## 七、蒙版、画布与 Agent 的实现重点

### 7.1 蒙版的显式提交

- 点击图下「抠图」创建 MaskSession，仅识别出灰度选区并叠加，背景原图始终可见。白=保留、黑=透明，中间灰度保留软边；与 inpaint 的“白=重绘”必须通过类型/字段区分，不能共用含糊的 mask 参数。
- 画笔坐标先 screen→world→object local→原图像素。首版若不支持旋转，工具明确禁用旋转；若支持则必须用对象逆变换，不能仅按 x/y 除宽高。笔划按轨迹连续插值，避免快速拖动形成散点断裂。
- 撤销/重做优先保存笔划命令 + 周期性栅格 checkpoint，不为每个 pointermove 保存整幅 4K RGBA；蒙版 session undo 栈和画布对象 undo 栈分开。蒙版位图存 IndexedDB 草稿、服务端保存版本，避免 data URL 塞入文档。
- 点蒙版栏「抠图」时冻结 maskRevision，等待该版本持久化 ACK，创建有幂等 key 的 apply task。按钮和编辑一起禁用，蒙版叠层保留并显示不定进度；结果生成用本次版本，不重新识别。
- 结果 alpha 建议 `A_out = A_source × M / 255`，防止对已有透明素材重新处理时恢复原透明像素。先统一 orientation、色彩通道和原像素尺寸，输出透明 PNG。当前 apply-mask 去除原 alpha 后直接覆盖，迁移时要加透明源图用例。
- apply 失败返回相同 MaskVersion，用户回编辑再主动提交新 revision；响应不确定先查 operation/task。离开后任务仍可服务端完成；重开恢复 mask session 或最终结果。

### 7.2 组布局、控制点与视频/文字

生成组使用持久 display order，四原始槽位与派生对象的归属独立。抠图提交只预约来源关系；成功插入时读取**源图当前位置**和当前组 layoutRevision，原图不移动，抠图结果按 `source → newest derived → older derived → next creative slot` 顺序建议排列，同组后续 x 坐标按实际宽度+间距累计，容器宽度重新计算。重复抠图顺序为本轮建议，需要产品确认；跨组自动挪动容易扰乱用户排版，首版不自动推移其他组，只保持组内相邻并提供定位结果。

图片单选、组选择用不同 hit target：点图片选单图，点组标题/边框选组；拖标题移动整组，拖图建议首版按组内布局约束移动或仅调整大小，拆组后自由拖动的规则不要未经确定就实现。控制点视口尺寸固定，变换结束写 width/height 并重置 scale，保持资产原尺寸不变。

工具栏用 DOM overlay，位置用 worldToScreen 算图片底部中心；相对于画布可用矩形 clamp，避开左工具栏、右对话和底输入框；图片在底部则工具栏翻到上方，窄窗口栏内滚动。相机变化和 ResizeObserver 后同一 requestAnimationFrame 更新。蒙版栏替换普通栏，保存并恢复焦点。

文字以 Konva.Text 展示，进入编辑时使用定位在同处的原生 textarea，支持中文 IME；composition 时不触发全局 Enter/Escape/Delete。编辑完成只提交一次命令，Esc 回退本次文本。Konva 官方也采用 DOM 文本输入覆盖画布的方式。[官方文字编辑示例](https://konvajs.org/docs/sandbox/Editable_Text.html)

画板首版建议为可命名、可移动的背景容器，默认 1024×1024，暂不裁剪内容、不做合成导出；此默认尚未经负责人确认。视频在画布内展示海报帧和播放标识，单击选中/拖动，独立播放按钮或双击打开 DOM `<video controls>` 预览；不在大量 Konva 对象中持续逐帧刷新，也不增加时间线。

### 7.3 Agent 共用操作接口与首例建议

最小推荐用例：**引用一张现有图片 → 说“把主体抠出来放旁边” → Agent 校验引用并准备蒙版 → 暂停到手动蒙版栏 → 用户调整并点「抠图」→ 服务完成透明结果并落位 → 对话提供结果和定位**。它验证引用、工具、暂停、恢复、结果归属，又不以未确认的自动抠图跳过已确认步骤。四背景方向串联可作为下一例，前置依赖更多，首版不再承诺合成海报。

工具白名单建议 `read_reference_metadata`、`prepare_subject_mask`、`await_mask_submission`、`query_task`、`locate_output`；`apply_cutout` 只能由已经持久的用户显式提交事件驱动。Agent 不得到任意代码、shell、文件路径、任意 URL 访问或全局资产查询工具。若未接视觉模型，只说已引用该资产并调用主体识别，不能描述看到了具体内容。

每次 run 固化 documentId、引用 objectId/assetId/revision、工具数上限与允许的生成轮数；建议首例最多处理 1 个引用、1 次主体识别、1 次显式 apply，失败不自动重做已成功步骤。这里是产品运行范围设置，不新增账号/权限系统。模型输出只作为有结构的操作提议，经 server schema 校验与 capability registry 后才执行；手动入口与 Agent 调用同一 operation service。

新增指令在执行中保留为草稿，用户可中断当前 run 后再发送，或等待当前 run 完成；不暗中修改已经执行中的提示词、引用与 maskRevision。对话中“已完成”至少需 OutputRef 存在、文件验证通过、画布对象关联事务已提交，不能根据 LLM 文本自行宣告。

优先技术验证清单：

1. **四方向与并发**：4 个不同 prompt，完整请求时间线；有限容量整组 admission；一失败、两失败、响应顺序打乱；上游 429/不确定超时；真实上游结果差异人工标注。费用/质量没有实测不填估算结论。
2. **提交及崩溃窗口**：DB 提交前后断连接、provider 收到后但返回前进程终止、文件完成但 DB 未 commit、DB commit 但 SSE 未到；恢复只能查询或完成本地确定工作，不暗中重复调用。
3. **事件与文档冲突**：同一事件 10 次、旧事件晚于新事件、离开文档/关浏览器、保存与结果同时到、旧 snapshot 缺少 completed task、task 超出全局历史页。用 taskId/docId 精确恢复，最终只一个结果对象。
4. **蒙版**：正向/反向笔刷、软边、透明源图、EXIF 旋转源图、缩放后画笔、4K 快速画、取消识别、退出后重开、apply 失败保留版本；显式提交前没有新透明图。
5. **画布规模与交互**：100 / 500 混合对象、50%/100%/200% 缩放、窄视口工具栏、组内派生、中文 IME、视频预览。记录设备和指标，不在 PRD 虚构帧率保证。
6. **Agent 工具边界**：无引用、多引用、引用被移除、asset 不可读、不支持能力、结构输出不合法、重复工具请求、重开等待确认 run；落位失败不得显示操作成功。
7. **迁移与真实能力**：同一个 legacy 文档的新旧渲染与引用核对；本地假上游契约通过后才跑受控真实 smoke；文生图/文生视频/抠图旧验证样本需要记录配置和时间，再新增四组/恢复验收。

建议新增的测试重点是领域状态与故障注入，而非逐个 DOM 样式复制实现。文档评审本轮不新增生产代码或真实推理测试。

## 九、提交给第二轮讨论的质询

1. 产品/交互：是否以“引用图片 → 准备蒙版 → 用户显式抠图 → 落位”作为第一条 Agent 完整用例？若要求全自动，请明确与已确认蒙版提交约束的关系，不能自行绕开。
2. 产品/用户：四图“同时”的验收是否接受一个调度窗口内并行请求，还是要求服务端实际推理重叠？第三方 API 的同步提交只能证明前者。能力未过门槛前，我建议明确不可用，不用逐张方案伪装。
3. UI/交互：组内图片自由拖动与抠图插入后全组顺延存在冲突。首版建议组内保持自动横排、允许组移动/单图选择，暂不拆组；请确认不会破坏主要整理任务。
4. 主持：首版工程优先级建议“持久契约 → 基本入口 → 四图组 → 蒙版 → Agent”，视频仅素材联通。Python 全量重写 + 任意 Agent + 视频时间线同期开工没有可控的最小完成条件。

本角色的结论是建议，角色共识不能替代负责人批准；未运行的功能和未经真实服务验证的能力保持「待验证」。
