# ⑤ 交互设计 · 第二轮质询与第三轮推荐

日期：2026-09-09。基于首轮独立评审，已阅读用户角色、UI 角色、全栈角色第二轮文件及主持 `PRD-创作平台与画布Agent-v0.4.md` 草稿。本轮与产品经理直接交换了计划触发方式的异议及回应。只输出评审文档，未修改产品或既有文件，未调用付费模型。

本文的“同意”是角色评审意见，不等同于负责人批准。UI 的浏览器观测由其报告提供，交互角色没有重新操作该线框，因此不将转引观测写成自己实测。

## 1. 同一问题：发送单图抠图需求后，是否再点击准备主体选区

### 各方起点

| 角色 | 原观点 | 具体理由 |
| --- | --- | --- |
| 交互首轮 | 方案展示后显式执行 | 需要看清实际引用、工具范围和结果数量；不能把任意自然语言自动扩大成工具执行 |
| 用户第二轮 | 一个“准备主体选区”按钮，避免再叠确认/执行/继续 | 希望普通语言解释下一步，不希望多次同义确认；最终仍在蒙版栏点击“抠图” |
| UI 第二轮 | 发送后自动准备，范围卡只告知 | 在单图、单能力的短流程中，中间“执行方案”增加无意义点击；保留最后的明确结果提交 |
| 产品经理直接回应 | 有效单图、明确意图、真实 LLM 计划通过校验后最多一次识别 | 用户发送已表达处理意图；歧义/超范围先澄清，不调用工具；透明结果仍只有一次显式提交 |

### 交互异议与直接回应

我最初向产品经理提出保留一个具体“准备主体选区”，删除泛化“执行方案”。担心的不是抽象权限，而是**LLM 尚未解释完需求时，系统并不知道要执行哪个有限范围；自动准备还可能把用户从正在编辑的其他对象强行拉走**。

产品经理回应建议采用 UI 方案，但以前置计划校验限制意图、引用、工具和次数。我接受这一取舍：在首条用例 A 的边界内，用户的明确发送意图足够触发识别，不必再加重复确认。我的原异议改由以下状态规则处理，而不是通过所有情况一律多一个按钮处理。

**最终推荐（本轮建议）：**

```text
显式引用一张图 + 明确抠图意图 → 发送
  → 真实 LLM 产生受限计划 → 服务端校验
    → 有效且仅用例 A 范围：显示范围卡，自动准备最多一次主体选区
    → 歧义 / 多引用 / 扩大目标：澄清，不执行识别
    → 无效计划 / 失效引用 / 能力不可用：明确失败或不可用，保留消息
准备完成 → 持久化等待用户状态
  → 当前上下文适合：显示该图蒙版
  → 用户已在别处编辑：卡片显示“选区已就绪 · 检查主体选区”，保留当前焦点
检查/调整 → 仅点击蒙版栏“抠图” → 生成透明图片 → 持久化并落位 → 完成
```

- 范围卡一句话即可：“处理「候选 02」；请你检查高亮保留区域；生成 1 张透明图片，放在原图右边，原图保留。”不要把内部工具名、continuation 或 schema 直接放进主流程。
- 自动准备发生在计划通过校验之后，不能“边规划边先识别”。若用户同时请求抠图、改背景和生成海报，不能静默删掉后两项并开始第一项，应说明首版可完成的范围并澄清。
- 只允许该计划的一次初始识别。识别失败不自动重试；用户点击“重新识别”创建明确的新尝试，未知识别状态只查原请求。
- 自动准备可以在后台进行；自动打开蒙版必须确保用户仍在同一文档、未切换选择、未开始文字编辑/另一蒙版/拖动。用户先发送 A 后选 B，不将当前选中 B 偷换为 A。提示中的“检查主体选区”是恢复/定位入口，不是再运行一次识别。
- “准备主体选区”保留为需要明确范围调整后的动作或保守替代方案，**不再是默认短路径上的额外按钮**。“执行方案”“确认方案”“继续执行”不连续叠加。
- 聊天里输入“继续”、刷新恢复、重新打开选区均不能消费最终生成动作。只有蒙版栏“抠图”可以提交透明结果。

### 保留的分歧与取舍

用户角色明确提出一个具体准备按钮，UI 与产品倾向自动准备；交互在上述条件下接受自动准备。用户角色尚未在本轮对修订作再次回应，因此不能记录为“五方一致赞成取消准备按钮”。

两种方案都保留既有最终“抠图”约束。自动准备减少一次点击，适合本轮单图明确意图；显式准备对多目标计划更容易解释范围，但可能让非常短的任务变慢。推荐首版自动准备，未来扩展多步/多能力时重新评估具体动作确认，不能把本次结论扩张为 Agent 可以无界自动执行。

产品经理随后直接确认接受全部新增条件：后台就绪不得抢焦点，检查选区入口只恢复场景，歧义/混合超范围先澄清，失败不自动重试。本文据此将这些条件记录为产品与交互之间实际达成的共识。

## 2. 对用户第二轮异议的回应

| 用户提出的问题 | 交互回应及修订 | 可观察检查 |
| --- | --- | --- |
| “蒙版”太专业 | 面向初次用户用“主体选区”“高亮区域将保留”；内部规范仍称蒙版；最终按钮继续叫“抠图” | 用户能说出高亮区域只是待保留范围，目前还没有透明图片 |
| 重试是否让人以为只补两张 | 接受“另生成一组 4 张”，旁注“原有结果保留，四张内容可能不同”；避免含糊的“重试” | 旧 2/4 组仍保留；点击后确实新建 4 个槽位；不能把它写成免费补图 |
| 未知状态会把用户困住 | 接受“查询结果”“返回我的画布”，保留最近已确认状态与当前待确认事实；允许非冲突的手动编辑 | 离开不取消/重发任务；返回恢复同一 requestId；等待很久也不自动变成失败可重试 |
| 默认保留草稿，少弹确认 | 接受。退出先持久化草稿，成功轻提示；只有草稿保留失败或明确丢弃才显示处理选择 | Esc 退出零透明结果；成功提示有真实保存依据；重开恢复同一源图版本的草稿 |
| 完成不要抢焦点 | 接受。只在用户仍停留当前抠图且没有新交互时选中新结果；其他情况下保留当前编辑，展示定位入口 | 输入中的文字、笔刷笔画与光标不被后台结果打断 |

**对主持 v0.4 草稿的修订建议：** §6 当前“有改动时保留/放弃/继续”不应每次退出都弹出。改为“默认保留草稿退出；保留失败才要求明确处理”，并区分“已保存到本机”和“已保存到服务端”，不能统称完成保存。该修改属于本轮建议，不改变手动显式提交约束。

## 3. 对 UI 第二轮异议的回应

### 浮层：接受末级停靠，固定退出与抠图按钮

接受 UI 的具体优先级，补入操作规则：

1. 正常状态图片下方居中，图与栏间隔建议 12 屏幕像素；横向在中央画布安全区夹紧。
2. 普通长工具栏可内部滚动；蒙版栏采用“退出固定区 / 可滚动工具区 / 抠图固定区”。最终“抠图”在任何滚动位置均可见，不让唯一提交入口滚走。
3. 用户主动进入蒙版或点击定位时可以微移视口腾空间；后台完成和用户输入期间不主动移动视口。
4. 下方仍无法容纳时允许停靠在输入框上方的安全区，显示源图缩略图或身份文字，例如“主体选区 · 候选 02”，并有“定位对象”。这属于同一编辑模式的例外布局，不是新增页面。
5. 对象完全不可见时隐藏笔刷工具区，只保留身份与定位；回到对象后恢复完整工具栏。不能允许用户看不见目标仍误以为在给另一张图涂抹。
6. Esc 先关闭栏内菜单，再退出蒙版并保留草稿。停靠布局切换不重建编辑会话，不清除草稿和撤销历史；焦点留在原有可用控件。

“抠图”固定区建议至少 72×40px，退出也保持可见。几何检查覆盖 1440/1280/1024px 窗宽、25%/100%/200% 缩放以及对象贴边。不得靠缩小整条工具栏使按钮可点击区域变小。

### 派生插入：固定原矩形，容器扩容

UI 报告了 v0.3 S15 的实际问题：插入第五个显示卡后，候选宽度由约 127px 变为 100px。这是 UI 的观测，本角色转引其结果。该表现与“原图保留、后续顺延”冲突，应作为材料及后续实现的明确修正项。

**推荐统一默认：24 个世界坐标单位。** 用于同组候选与派生项的相邻间距；不是屏幕像素。首轮交互与第二轮 UI 已使用 24，留出贴边选框及来源标签的辨识空间。主持草稿的 16 也可成立，但同一规格必须只保留一个默认。本轮推荐 24，具体值是设计建议，不是用户确认约束。

默认布局规则：

- 保存每个现有对象的 x/y/宽高；新增派生图不能修改源图或其他原候选的宽高。
- 派生图按源图显示高度等比展示，保留真实资产尺寸；不改变源图分辨率和比例。
- 顺序推荐 **源图 → 派生 1 → 派生 2 → 下一候选**，按派生创建顺序追加。组宽度增长，后续候选仅水平顺延；对话中的原四候选继续 2×2 预览，派生另用单图结果卡。
- v0.4 当前“最新派生最靠近源图”能让最新结果更近，但会不断挪动此前的派生结果。推荐改为创建顺序，结合新结果选中/定位减少寻找成本，使已存在布局更稳定。若主持保留最新优先，需明确这是尚有取舍的建议值，并同步所有文件。
- 四方向 slot 永远只有 01–04，派生名称如“候选 01 · 抠图 2”；组摘要显示“创意候选 4/4 · 派生素材 2”，不出现 6/4。

可观察验收：插入前后原图 x/y/宽高一致，原候选宽高一致；新结果位置满足右邻顺序与 24 单位间距；组宽度增长，原候选顺序不变；刷新不再次插入；撤销只撤回这次派生及其造成的布局变更。

产品经理已直接回应接受统一 24 世界单位与派生按创建顺序追加；这与 UI 第二轮建议一致。主持仍需同步 PRD/技术方案中的旧 16 单位及最新优先表述，不能只在评审纪要改值。

## 4. 对全栈第二轮异议的回应

| 全栈要求 | 交互回应 | 产品状态表达 |
| --- | --- | --- |
| 真实 LLM 计划，不能把关键词路由称 Agent | 同意。自动准备仍必须在真实模型输出及服务端验证后；失败/澄清/有效计划有独立路径，不为演示用模板冒充 | 正在理解需求 → 范围明确并准备 / 需要补充 / 暂不可执行 |
| `awaiting_user` 持久化且不占 worker | 同意。恢复同一源版本、蒙版版本和等待节点；卡片“检查主体选区”只恢复界面，不能重调模型/识别 | 等待你检查主体选区；可离开后继续 |
| continuation 只能被正确生成提交消费 | 同意。按钮在途禁用；网络丢响应查询同一提交；聊天继续和刷新没有最终提交权限 | 生成中 / 结果待确认；禁止按钮重复触发 |
| 资产完成与落位完成不同 | 同意。资产有效而落位失败展示结果预览与“重新同步画布”，同步只做落位，不再生成 | “结果已保留，尚未加入画布” |
| 无法保证跨供应商 exactly-once | 接受并收窄首轮“只一次”措辞：本地去重、刷新不重派、未知先对账；是否可安全重发取决于上游证据 | 不写“绝不会重复计费”；新一轮明确是新调用 |
| 旧 snapshot 保存会覆盖 worker 落位 | 同意操作级持久化与 revision 冲突反馈；草稿必须保留 | 版本冲突时提示内容有更新，保存自己的改动后重新同步，不能假显示已保存 |
| 四个本地协程不等于供应商物理同时推理 | 同意。UI 只承诺经能力验证的单批四方向或同窗口四路提交；不能依据动效声称 GPU 并行 | 四槽同组生成中；真实派发证据另作为能力验收 |

我将产品/交互实际达成的自动准备规则直接发给全栈，全栈随后确认兼容并接受删除额外执行点击。其具体补充是：plan/run 与唯一 detect task 事务内持久化，run step 唯一约束防重复触发；前端模式会话 epoch 只决定是否进入蒙版，不影响后台持久任务；最终 apply 仍原子消费 continuation 并创建任务。全栈也接受固定原矩形并扩组，24 单位与创建顺序由主持统一后同步技术稿。该回应是本轮实际收到的意见，不是由旧稿推定。

## 5. 修订后的完整关键状态表

| 当前状态 | 触发与前提 | 反馈与后续状态 | 允许离开/恢复行为 |
| --- | --- | --- | --- |
| 草稿输入 | 一张有效显式引用，用户发送明确需求 | 固定引用快照，规划中 | 可编辑下一条草稿；旧引用不随选择变化 |
| 规划中 | 真实模型返回计划 | 校验通过自动准备一次；歧义则澄清；无效则失败 | 刷新只查保存的运行，不重调模型 |
| 主体选区准备中 | 受限识别任务在途 | 源图与状态卡显示准备；不新增透明图片 | 可离开；用户切换上下文不强行抢回焦点 |
| 结果待确认 | 原请求是否接受/完成未知 | 保留最后状态，提供查询 | 可返回我的画布；不自动重新派发 |
| 等待用户 | 蒙版有效，已持久化等待节点 | 显示高亮保留区；“抠图”可用 | 退出默认保留草稿；重新打开恢复，不生成 |
| 草稿退出 | Esc/关闭/切换模式 | 保存成功提示草稿保留，普通选中 | 保存失败才显示留在编辑/明确放弃选择 |
| 生成中 | 蒙版栏“抠图”，有效源/蒙版/等待节点 | 固定当前版本；编辑/重复提交禁用 | 允许离开；查询原任务；不能自动重调模型 |
| 已产出、待落位 | PNG 已持久化，但文档落位未成功 | 有效预览 + 尚未加入画布 | “重新同步画布”只修复落位 |
| 完成 | 资产、放置和会话状态一致 | 新结果右侧追加，来源清楚，按上下文选择或提示 | 刷新恢复一次；撤销记录落位撤回状态 |
| 源对象失效 | 计划/等待/生成期间源被替换或移除 | 尚未提交步骤暂停；已生成资产保留 | 更新引用/显式加入；不复活源图，不偷换资产 |

## 6. 第三轮最终推荐与边界

1. 采用用例 A 作为首条 Agent 工程验证闭环，价值在真实计划、显式引用、可恢复人工检查、可追踪结果；它对真实体验者的增益仍待测试，不能编造用户研究结论。
2. 默认发送后的有效受限计划自动准备主体选区；去掉泛化“执行方案”，保留唯一最终“抠图”。源图模式切换不得打断用户新交互。用户建议的显式准备按钮作为保守替代方案保留在讨论记录。
3. 默认退出保留真实草稿，失败才保护；未知状态只查原任务但允许离开继续；正常编辑不可被单个未知任务锁死。
4. 接受 UI 的图下优先、固定抠图区、安全区底部末级停靠及源图身份规则。
5. 建议固定原对象尺寸、组扩容，统一 24 世界单位；派生按创建顺序追加。16/24 和派生新旧排序属于尚需主持统一的建议，不能在实现中形成两套规则。
6. 明确本地幂等与第三方请求未知窗口，禁止承诺跨供应商绝对仅调用一次；明确任务、资产、落位、文档保存与草稿状态分别成立。

这些推荐不新增本轮审批事项，供主持整合为一致的可交互 PRD、技术状态机和验收条目。
