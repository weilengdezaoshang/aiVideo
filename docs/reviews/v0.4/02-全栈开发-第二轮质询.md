# ② 全栈开发 · 第二轮具体质询与回应

日期：2026-09-09。已读产品经理、交互设计首轮与主持 v0.4 PRD 草稿。本轮是方案讨论，未运行真实模型或修改产品代码。第一轮证据见 [全栈独立评审](./02-全栈开发-独立评审.md)。

## 共同问题一：首条 Agent 会不会只是抠图按钮包装？

**对产品的异议：** 用例短本身不是问题，但“自然语言→固定文案→自动点抠图”不足以验证 Agent。必须让真实 LLM 输出受限结构化计划，并独立验收无引用、多引用、超范围意图、失效引用、模型格式错误与暂停恢复；否则不能将一键抠图改名为 Agent。

**回应与最终推荐：** 经产品/交互实际质询与主持确认，接受：显式引用一张图且完整意图明确→真实模型计划→服务端校验后自动准备一次蒙版→持久化 `awaiting_user`→用户在蒙版栏点“抠图”→PNG 和落位。删除中间草稿的额外“准备蒙版”点击；我的核心要求是真实计划、范围和暂停恢复，并不要求额外按钮。增加计划校验器、ToolCall 记录与单次消费的 continuation；无需为了表现“智能”加入背景、图像问答、搜索或自主反复尝试。

- `clarify`、`plan`、`unsupported` 是模型输出的互斥类型；没有引用不能先调用识别工具。
- 模型只选择服务端给出的引用句柄，例如 `ref_1`，不能自行传磁盘路径、URL 或另一个文档的 assetId。
- 计划显示处理对象、最多一个识别任务、一个等待节点、一个透明结果；本用例图像生成轮次为 0。
- 模型计划运行一次并持久保存；刷新不能自动再次调 LLM。格式校验失败本轮建议明确失败，用户可重试，不隐式循环纠错。
- `awaiting_user` 不占 worker；浏览器恢复后继续同一个 session 和 mask revision。聊天“继续”只定位蒙版，不能获得 apply token 的消费权。
- 仅一个有效显式引用且整个用户意图都在首例范围，才自动识别一次；歧义/混合越界先澄清，不删去不支持目标后部分执行。合法计划和唯一 detect task 事务落盘，重复计划事件或重连不二次识别；失败显式重试，unknown 只查。
- 用户已经在编辑文字/另一蒙版时，后台准备不抢焦点与当前选择，只给“检查主体选区”入口；前端 mode epoch 只决定是否进入蒙版界面，不改后台任务事实。
- 真实模型的 20 条起始意图集与 Mock 状态机测试分开。发布要求禁止工具调用场景零副作用；有效计划比例是目标，不是本次实测结果。

**执行成本：** 额外成本集中在一个受限 planner、引用句柄映射、持久暂停、错误视图和评估集；这些可直接复用到下一条多步工作流。相比直接把 rembg 当任意 tool 暴露，增加的是必要可控边界。

## 共同问题二：整组重生与补失败方向

**对产品/交互的异议：** “重新生成一组”更容易实现，但会重新产生四张，不能写成“免费重试”，不能暗示已有成功资产会参与/被复用。未知调用也不能因为用户等得久就转成普通重试。

**回应：** 接受首版“部分完成→旧组保留→显式新组 4 张”，新组记录 `retryOfGroupId`，使用新 operationId。复用原 prompt 和已固定方向快照；用户更改需求则作为全新创作组，不能假称同一次失败恢复。UI 文字明确“新建一组 4 张，保留已有结果”。

| 方案 | 真实工程成本 | 产品取舍 |
| --- | --- | --- |
| 新组 4 张 | 复用已实现的整组提交；新增父组引用即可；仍需新任务幂等 | 保留旧组、契约清楚，但再次调用 4 张的时间/费用可能更高 |
| 仅补失败方向 | slot attempt 版本、多次终态、旧 attempt 晚到隔离、单槽容量/取消、组修复状态和原 prompt 追溯；需要精确解释收费与图像一致性 | 少重复生成，但容易混淆“固定四图”和“补图”；首版延期合理 |

`unknown` 只允许查原 externalRequestId/operationId；只有证明上游未接受才能安全重发同一次未执行意图。无法查询时保留“结果待确认”，人工新创作也必须明确不是原请求的安全重试，不能承诺不重复计费。

## 共同问题三：Python 迁移与后台结果一致性

**回应交互对唯一落位/撤回状态的要求：** 同意，且由服务端实现。Task 的执行、Asset 的存在、Placement 的应用是三个状态；新增 `placements` 唯一 `(taskId, outputIndex)`，状态 `pending/applied/suppressed/needs_placement/reverted`。撤销写补偿记录，不能只在前端删对象。旧完成事件重新到达也不能覆写 `reverted`。

**异议：** 不能保留旧全量 JSON 保存作为新编辑器的常规写路径。即使有 SQLite task 表，旧 snapshot 仍会覆盖 worker 新插入的对象。单靠 BroadcastChannel 检测多标签页也挡不住同一页面与 worker 竞争。

**推荐具体合同：**

1. 新 `/api/v2` 只有 Python 拥有文档/对象/资产/任务/会话；旧 Express JSON 数据只读迁移，切换时停旧文档写入口。旧生成实验入口临时保留时，只能向新资产域幂等导入，不直接写新文档。
2. 前端发送 `operationId + baseRevision + commands[]`，SQLite `BEGIN IMMEDIATE` 后检验版本，应用文档修改、递增 revision、写 event/outbox，单事务提交。
3. worker 落位使用相同 operation service。完成文件已入库但落位冲突时只重试数据库落位，绝不重新生成。
4. 前端 GET snapshot 返回 `eventCursor`；以文档为范围从 cursor 接 SSE；增量事件按 entityVersion 去旧重放。历史缺席不代表失败，不能再依靠活动任务 snapshot 判丢失。
5. 普通保存冲突返回 409 + currentRevision，保留本地草稿并重取基线；不以最后写入覆盖。单机 SQLite 不意味着 API/worker 同时写无需事务。
6. outbox 保证业务数据与待通知事件在本地一起提交，SSE 游标保证可补发；它们都不能独立保证第三方模型 exactly-once。外部请求提交与结果记录之间存在不可跨库事务化的未知窗口。

## 向主持反馈的规范冲突

- v0.4 草稿 A12 的“均不重复计费提交”应限定为“客户端重连/刷新/重复事件不产生新派发；上游未知时只对账”。第三方无幂等或查询能力时，不承诺普遍 exactly-once。
- 原首轮全栈建议工具栏下方不足时翻到上方；本轮遵循主持/交互草稿，改为优先微移视口、必要时安全区底部停靠，保留图片下方规则。
- 主持采用产品/交互第二轮统一：派生按创建时间追加源图派生链尾、间距 24 个世界单位；固定原候选矩形，扩组不缩卡。文字默认 32px；蒙版默认保存草稿退出，只有保存失败才出现保护选项。中间草稿的最新在前/间距 16 不再采用。
- 一轮“同时生成”只能按可证据验收的定义承诺：原生四方向 batch 或同一窗口四路派发。不能从 4 个本地协程推断第三方 GPU 推理时间一定重叠。

已通过协作消息将异议发给主持；首次直接发给产品角色时工具返回 `agent thread limit reached`，随后产品和交互角色唤醒后已直接来回质询。全栈明确接受自动准备的上述条件，主持已采用并要求同步技术稿。最终共识不是负责人批准，功能仍需真实验收。
