# GenCanvas 产品定位、产品形态与 PRD

版本：v0.2 · 日期：2026-09-08 · 状态：产品收敛建议稿，尚未代表用户批准或发布承诺。

> 后续访谈已明确平台方向、无限画布 + Agent 的首版重心与工作台入口，参见 [v0.3 阶段性 PRD](./PRD-创作平台与画布Agent-v0.3.md)。本文保留为历史建议稿，用户画像与首版范围不作为当前已确认决策。

本文基于当前仓库与用户已完成的验证，规划下一阶段产品化。工作代号沿用 GenCanvas。旧版《PRD-生成式创作画布》与《开发计划》保留为实现背景；本稿提出新的范围建议，评审通过后再同步开发排期。

## 1. 决策摘要

**产品定位：面向有持续视觉素材需求的独立创作者，提供一个可持续编辑的 AI 视觉素材工作台。**

**用户承诺：在一个项目里，从想法或已有图片出发，生成图片、提取主体、生成视频片段，比较并保留结果，导出可继续使用的素材。**

产品形态采用桌面浏览器 Web 应用：项目入口 + 项目画布 + 上下文工具 + 素材库 + 任务中心。一个项目暂时对应一张画布，复用当前文档模型。画布承担素材组织和版本比较，输出以单个素材为单位。

首版产品闭环为：创建项目 → 生成或导入 → 挑选 → 抠图或再次生成 → 导出 → 下次继续。

首版交付图片、透明 PNG、视频片段。海报文字排版、成品短视频剪辑不计入首版承诺。图生视频作为下一步能力单独验收，不把文生视频已验证等同于图生视频已验证。

部署优先沿用单人自部署、用户配置自己的模型服务。云模型调用与本地处理允许并存；使用云模型时相关输入会发送到所选服务，不能宣称全部数据离线。暂不新增账号、支付、多人协作。

## 2. 事实、判断与待验证假设

### 2.1 当前依据

| 项目 | 当前证据 | 本稿如何使用 |
| --- | --- | --- |
| 文生图、文生视频、抠图 | 用户明确表示流程已验证 | 作为首版能力基础；具体模型、样本和质量边界仍需补入验收记录 |
| 无限画布、素材库、文档保存、生成状态、变体、重绘、视频对象 | 当前代码与开发计划存在相应实现 | 视为已有基础，不等于本轮已重新完成真实环境验收 |
| 抠图可修正蒙版并产出透明图 | `web/canvas/flows/cutout.js`、服务端 cutout 路由 | 将抠图纳入核心流程；人像/商品等类别分别验证质量 |
| 图像与视频服务能力不同 | Provider 接口提供可选参考图；当前 cloud provider 的视频实现不提供生成能力 | UI 按实际服务能力开放入口，不能用一个全局模型列表暗示全部功能均可用 |
| 旧 PRD 以 AI 爱好者、自部署画布为主 | 旧版文档 | 保留画布与部署方向，进一步明确使用任务、输出和验收 |

本轮仅进行代码与文档梳理，没有重新调用模型验证质量。旧文档关于市场空白、竞品全部闭源、许可变更和合规的断言不作为本次定位依据；若后续需要竞争研究或商业发布决策，应另行核实。

### 2.2 产品假设

尚未收到目标用户的进一步选择，本稿暂沿用旧方向，聚焦“有实际交付需求的独立创作者”，优先观察内容配图、人物素材和短视频片段任务。以下均需试用验证：

- 用户反复生成与加工素材时，需要保留上下文、比较结果并复用，而非只下载一次。
- 在同一项目完成至少两种操作，能够减少切换工具与重新导入的负担。
- 首批用户愿意接受自部署/BYOK；需要无配置即用的用户不适合用该首版验证获客。
- 当前抠图对首批用户的主体类别足够可用，且手工修正成本可接受。

若最终选择电商用户，首要验收需改为商品结构、文字/Logo、颜色保持与商品抠图质量，并增加固定尺寸合成输出；若选择专业设计师，则提高精确编辑、参考控制与资产复用优先级。两种方向都不直接混入首版。

## 3. 用户与核心任务

### 3.1 首要用户

独立内容创作者或小团队中的实际制作者：能描述视觉需求，有周期性的素材产出任务，愿意使用 AI，但不希望每次操作都重新配置工作流。首版仍为单人使用，不提供团队权限。

用户的任务表达：

> 当我要为一个内容主题准备视觉素材时，我希望在同一工作区生成、比较和加工图片与视频片段，并保存可复用的结果，以便更快把素材带入后续排版或剪辑工具。

### 3.2 三个首版场景

| 场景 | 起点 | 核心操作 | 完成标准 |
| --- | --- | --- | --- |
| 内容配图 | 一段画面描述 | 文生图 → 比较候选 → 调整描述重试 → 导出 | 下载用户认可的完整分辨率图片 |
| 主体素材 | 上传图片或生成图片 | 抠图 → 擦除/恢复 → 检查透明边缘 → 导出 | 得到透明 PNG，源图保留 |
| 视频素材 | 动作、场景和镜头描述 | 文生视频 → 等待 → 播放检查 → 导出 | 得到可播放的视频文件，明确为单个片段 |

三条路径均可独立完成，不强迫用户把三个功能依次用一遍。项目负责把相关素材组织在一起。

### 3.3 产品价值的取舍

| 方向 | 本阶段决策 | 原因 |
| --- | --- | --- |
| 多模型生成工具箱 | 作为底层能力 | 仅增加模型数量无法验证完整创作价值 |
| 项目画布工作台 | 主产品形态 | 已有实现可复用，能保留源图、候选与派生素材 |
| 自动设计 Agent | 后续实验 | 需要额外验证规划、编辑与自动执行质量 |
| 专业图像编辑器/视频剪辑器 | 暂不扩展 | 文字、图层合成、时间线等会显著扩大验收范围 |
| 模板化垂直工具 | 等首批场景验证后选择 | 需要先明确重复任务与主体类别 |

开源、自部署、BYOK 是交付方式和控制权特征；主价值要用任务完成效果证明。

## 4. 产品形态与信息架构

### 4.1 页面结构

```text
项目首页
├─ 新建项目
├─ 最近项目：名称、封面、更新时间
└─ 设置：图像服务、视频服务、抠图服务及连接状态

项目工作台（一项目一画布）
├─ 顶栏：项目名称 / 保存状态 / 任务 / 导出
├─ 左侧工具：生成图片 / 生成视频 / 导入素材 / 素材库
├─ 中央画布：源素材 / 候选结果 / 处理中卡片 / 错误卡片
├─ 选中对象工具：抠图 / 复用描述 / 下载 / 更多
└─ 右侧按需展开：生成配置或素材详情
```

主流程必须有可见按钮，右键与快捷键作为加速入口。空画布显示“生成图片”“生成视频”“导入图片”；服务未配置时，点击进入对应配置引导并保留输入。

### 4.2 交互原则

- 默认显示描述、比例/尺寸、数量；视频另显示时长。模型在对应生成面板中选择，高级参数折叠。
- 支持的尺寸、时长、参考图等以所选服务实际能力为准，不展示无法执行的固定选项。
- 选中图片显示抠图等可用动作；选中视频显示播放、下载与生成信息。关键动作无需记忆快捷键。
- 等待生成时，用户可以移动卡片、浏览其他素材或继续提交；结果替换对应卡片并保留位置。
- 每次加工产生新素材，原始素材保留。源素材与结果在空间上相邻，并在详情记录来源。
- 图片支持放大查看；透明图以棋盘格预览；视频默认静止，用户主动播放。
- 区分“从画布移除”与“永久删除素材”；前者可撤销，不删除磁盘资产。

## 5. 首版功能需求与验收

优先级定义：P0 为首版 Beta 门槛；P1 在闭环验证后推进；P2 为保留方向。优先级不表示从零开发，已有功能先做差距验收。

| ID | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| R01 | 项目创建、命名、列表和继续编辑 | P0 | 创建两个项目，各放入不同素材；重开后名称、内容、位置不串项目 |
| R02 | 文生图 | P0 | 从空项目提交有效描述；完成后能预览并下载真实图片；描述和实际模型可回查 |
| R03 | 文生视频独立入口 | P0 | 无参考图即可提交；仅展示后端支持的时长等选项；最终产物能播放和下载，演示占位不计成功 |
| R04 | 图片导入 | P0 | PNG/JPEG/WebP 经校验后可加入画布；错误格式或超限文件有明确原因，失败不留伪素材 |
| R05 | 抠图与蒙版修正 | P0 | 支持识别、擦除、恢复、取消和应用；修正与原图坐标对齐；导出 PNG 保留 alpha，源图不变 |
| R06 | 基础画布与结果比较 | P0 | 平移、缩放、选择、移动、删除/撤销可用；源图与派生图能同时查看；无须进入高级操作即可比较 |
| R07 | 导出单个素材 | P0 | 图片导出原始资产；抠图导出透明 PNG；视频导出真实视频文件；失败给重试入口，不把缩略图当原图 |
| R08 | 保存与刷新恢复 | P0 | 已显示“已保存”的编辑在刷新后保留；任务完成后刷新能正确落位；保存失败持续可见并可重试 |
| R09 | 任务管理 | P0 | 排队、处理中、成功、失败、取消可区分；失败保留输入；用户主动重试创建新任务；取消后不错误插入完成结果 |
| R10 | 服务配置与能力匹配 | P0 | 图像、视频、抠图各自显示是否可用；密钥不明文返回；不支持的动作在提交前说明；切换服务不清空项目 |
| R11 | 素材库与来源信息 | P0 | 已生成/导入/抠图结果可再次加入项目；记录来源素材、操作类型及适用的生成参数；重开可查看 |
| R12 | 图生视频 | P1 | 独立完成参考图到真实视频的验收；失败不退化成未告知用户的文生视频 |
| R13 | 图生图、局部重绘、批量候选 | P1 | 按具体服务验证质量和支持情况后作为正式能力开放；已有实现保留，不作为本版新增范围 |
| R14 | 基础合成与固定尺寸导出 | P1 | 先验证用户需求；若立项，另写画板边界、缩放、图层顺序和合成导出规格 |
| R15 | 提示词收藏、模板、标签 | P2 | 依据重复使用的真实任务决定优先级 |
| R16 | SVG 转换 | P2 | 保留现有实现作为扩展工具，不作为核心卖点；当前实现为 ImageTracerJS，旧 vtracer 方案不再作为开发依据 |

### 5.1 抠图的专项边界

抠图输出是独立的透明素材。首版不把“画布上放在另一张图上”视为已具备背景替换或合成导出。

验收至少覆盖当前服务实际面向的主体类型，并记录毛发、手持物品、饰品、透明/半透明区域与复杂背景。人像通过不能代表商品通过。不承诺自动识别无误，用户须能修正或取消。

蒙版编辑中切换项目或关闭编辑模式时提示未应用的修正；未应用蒙版不纳入首版跨会话恢复承诺。识别失败与应用失败分别提示，失败不能覆盖源图。

### 5.2 任务与异常规则

| 事件 | 用户看到的行为 |
| --- | --- |
| 参数不支持 | 提交前指出具体不支持项；保留描述，允许改选服务或参数 |
| 没有真实进度 | 显示阶段与已等待时间，不伪造百分比 |
| 双击提交或网络响应不明 | 同一次提交避免重复建任务；先查询状态，不能自动再花一次生成费用 |
| 断网后恢复 | 显示断线状态，重连后按任务记录对账；同一结果不重复落位 |
| 服务重启、任务无法恢复 | 标记为中断并提供主动重试，不无限转圈 |
| 用户取消 | 区分已取消与取消请求中；不能保证外部服务停算时如实说明，不承诺退费 |
| 批次部分失败 | 保留成功结果，失败项独立重试 |
| 素材丢失 | 显示丢失状态与来源信息，不能静默显示为空白成功卡 |
| 多标签页编辑同一项目 | 首版提示并限制为单一可写编辑页，避免静默覆盖 |

### 5.3 数据与保留规则

- Project 复用现有 CanvasDoc，保存名称、对象顺序、位置与更新时间；暂不增加多画布层级。
- Asset 表示持久化文件，区分图片、视频、透明图片；同一资产可被多个画布对象引用。
- Operation/Job 保存操作类别、输入资产引用、有效参数、实际服务/模型、状态和输出引用。抠图也需要进入来源记录，不强行复用生成参数。
- CanvasObject 表示资产在项目中的摆放实例；删除实例不等于删除资产。
- 被项目引用的素材必须受保护，历史裁剪不能让项目破图；永久删除需先处理引用关系。
- 保存状态以服务端确认作为依据；退出时尽力保存不能宣称崩溃零丢失。最近未确认的编辑存在丢失窗口，恢复能力以验收结果为准。
- 只保存复现所需配置标识，不把 API Key 写入素材元数据或日志。复用参数代表重新发起相同配置，不承诺跨模型版本像素一致。

## 6. 非功能要求

以下为拟定验收目标，不是本轮已测结果。发布记录必须写明设备、浏览器、样本量与服务配置。

| 维度 | Beta 验收目标 |
| --- | --- |
| 基础交互 | 在指定基准设备、100 个对象含 20 张 2048px 图片的项目上，平移缩放无持续超过 100ms 的停顿；首次有意义内容本地热启动 ≤2 秒 |
| 保存 | 停止编辑约 2 秒后发起保存；收到成功响应才显示已保存；服务端写失败可见 |
| 生成等待 | 提交后 300ms 内有本地反馈；生成耗时按模型统计，不设脱离实际后端的统一出图承诺 |
| 状态更新 | 正常连接下，客户端收到事件至界面更新 ≤200ms；断线恢复后主动对账 |
| 浏览器 | Beta 优先验收桌面 Chrome、Edge，记录具体版本；Safari 完成测试后列为正式支持 |
| 可访问性 | 核心操作可键盘访问，焦点可见；状态不只靠颜色；关闭对话框后焦点返回触发位置 |
| 运行与数据 | 服务重启后已保存项目和已完成素材可恢复；外部服务不可用时仍能浏览与导出本地素材 |

## 7. 产品验证与指标

**主指标：每周完成有效素材交付的活跃创作者数。** 单人试用阶段先统计有效交付会话数，不从开发者自测推算市场留存。

有效交付：用户在一个任务会话中完成生成或抠图，导出至少一份结果，并在试用反馈中确认用于实际任务。下载只是交付代理指标，未删除不等于满意。

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 首次交付完成率 | 完成首次有效交付人数 / 开始试用人数 | 判断入口与完整流程能否独立完成 |
| 到首次导出的时间 | 首次操作到首次成功导出；配置、排队、推理分别计时 | 区分配置障碍、交互摩擦和模型耗时 |
| 跨工具使用率 | 同项目使用至少两种核心操作的活跃项目 / 活跃项目 | 验证整合工作台是否有价值，不强求所有任务跨工具 |
| 输出接受率 | 用户明确接受的结果 / 用户实际评审结果 | 评估质量，不以历史保留率替代 |
| 任务成功率 | 成功任务 / 成功与失败任务总数，取消单列 | 按功能、服务和模型定位稳定性 |
| 再次使用 | 首次使用后 7 天内因新任务返回的人数 / 已满观察期的首次用户 | 观察持续任务价值 |

建议首轮邀请 5 位符合目标画像的用户，每人带 2 个真实任务，连续观察一周。暂定继续投入门槛：至少 4 人无需开发者代操作完成首次导出，至少 3 人确认有实际使用的素材，至少 3 人因第二个任务再次使用。小样本仅用于方向筛选。

补充最小事件：project_created、operation_submitted/completed/failed/cancelled、asset_exported、output_accepted；用 projectId、operationId、assetId 关联。默认本地记录，不新增远程遥测。已有 traces 可复用，但需要补齐抠图、导出与明确反馈；费用未知显示未知，不用零代替。

## 8. 迭代计划与退出条件

### M0：能力验收清单

把三条已验证流程记录为可重复案例：服务/模型、输入、参数、输出、耗时和失败边界。明确文生视频对应的实际服务与入口；分别记录人像和其他主体的抠图效果。交付为三条真实案例和能力矩阵。

### M1：单项目交付闭环

完成 R01–R07、R10 的缺口：统一入口、项目名称、图片/视频模式、上下文工具与单素材导出。退出条件为新用户能从空项目独立完成三种场景，不依赖开发者切配置或调用 API。

### M2：可继续使用的 Beta

完成 R08、R09、R11 与数据保留规则，覆盖刷新、断网、服务重启、取消、失败重试、原素材删除关联。退出条件为 P0 验收通过，关键项目数据无已知丢失缺陷；实施代码变更后运行 `npm run verify`，并补做真实服务端到端验收。

### M3：真实用户验证

执行一周试用，记录完整任务及二次使用。若用户只使用一个独立功能，重新评估画布的必要性；若主要反馈集中于排版或商品合成，决定是否转向垂直场景，再进入 R14。排期以差距审计结果估算，本稿不预设开发天数。

## 9. 评审时需要收敛的事项

| 事项 | 当前建议 | 改变时的影响 |
| --- | --- | --- |
| 第一类用户 | 独立视觉内容创作者 | 电商方向需要商品一致性与合成输出；专业设计方向需要更强编辑控制 |
| 首版输出层级 | 可复用素材 | 若要求成品海报/成片，需另立编辑与导出范围 |
| 第一阶段交付方式 | 单人自部署 + 自备服务 | 若转公有 SaaS，身份、隔离、计费与运营要求需单独立项 |
| 视频范围 | 文生视频 P0，图生视频 P1 | 若已有图生视频真实验收证据，可提升为 P0，但不自动视为已通过 |
| 产品名称 | GenCanvas 作为工作代号 | 品牌名称可后定，不阻塞闭环 |

许可与商业模式暂沿用仓库现状，不在此次 PRD 中做未经确认的变更。先验证用户愿意持续使用的工作流，再讨论托管订阅或团队方案，不把商业化假设写成已成立结论。
