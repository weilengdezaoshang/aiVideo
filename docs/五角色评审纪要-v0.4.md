## 2. 第一轮：各角色最多五个关键问题

| 角色 | 问题 1 | 问题 2 | 问题 3 | 问题 4 | 问题 5 |
| --- | --- | --- | --- | --- | --- |
| 产品 | Agent 无首条完成用例 | 四方向差异与同时执行不可验收 | 保存、生成、落位没有统一恢复门槛 | 工作台/视频入口扩大范围 | 导出、画板、文字缺最小合同 |

最直接的代码证据：画布生成强制 `batchCount=1`，任务管理器按 `for + await` 串行处理 batch，现有 Cloud/ComfyUI 容量配置也不足以证明四路并发。不能把这些现状通过改文案验收成 W15/W16。

最直接的线框证据：UI 实际测得 S39 候选宽约 127px，S15 插入派生结果后等分五列降到约 100px。已确认要求是后续顺延与容器扩展，应保持原四图矩形，而不是压缩原图适配原容器。

## 3. 第二轮：围绕同一问题相互质询

### 3.1 首条 Agent 是完整用例，还是抠图按钮的包装？

产品提出 A“引用单图、协作抠主体、放到旁边”和 B“抠主体后生成四个背景方向”，推荐 A。全栈质疑：如果只有模板话术和固定前端分支，不能验收为 LLM Agent；必须看到真实结构化计划、缺失引用澄清、非法工具拒绝和刷新后的人工暂停恢复。用户质疑：手动抠图本身很短，额外计划确认不应增加无意义点击。

产品回应：A 的价值在统一自然语言目标、显式引用、解释当前阶段、让用户接手和恢复；不以“长工具链”证明价值。真正的完成是透明 Asset、正确 Placement 和对话预览同时成立。全栈接受，但保留真实模型计划与异常验证门槛。B 在 A 和四方向能力分别通过后再做，不能把背景候选写成自动合成海报。

### 3.2 发送后自动准备蒙版，还是再点一次准备？

初始产品/交互草案保留“准备蒙版”或执行入口。用户希望最多一个“准备主体选区”按钮。UI 主张范围卡只告知，发送明确需求后自动准备，以减少额外点击；最终透明生成仍只有蒙版栏“抠图”。

交互提出自动切换模式可能打断文字或另一个蒙版，不能偷偷把用户后来选中的 B 替换回 A。产品、交互与全栈直接讨论后达成条件：完整意图明确、一个显式引用、真实 LLM 有效计划、服务端能力与范围校验通过，事务建立唯一识别任务，自动最多一次；歧义及混合越界请求先澄清，零工具调用。后台就绪不抢焦点，显示“检查主体选区”。等待用户状态持久化，刷新不重新规划或识别。

用户第三轮读取回应后有条件接受自动准备，不再坚持默认准备按钮；接受条件为阶段与来源可见、不抢焦点、恢复不重做、最终仍由蒙版栏提交。本轮推荐据此删除默认额外准备按钮。

### 3.3 部分失败为何不只补失败方向？

交互建议先保留旧组，另生成完整四图组。全栈解释局部补生成增加槽位 attempt 版本、过期响应隔离、单槽替换、费用说明及供应商能力契约；整组重生依赖更少且不损失成功图。用户担心“重试”被理解为免费或只补两张。

收敛建议：按钮“另生成一组 4 张”，旁边说明旧组保留、新调用可能产生费用、内容可能不同；服务端新 key/new group，记录 retryOfGroupId，保留旧方向快照。未知结果只查询原任务；允许离开、浏览与手动编辑，不让无限等待阻断整个文档。

### 3.4 原图旁的多个派生结果如何排列？

UI 提出保持世界坐标尺寸，扩容与顺延，不能等分五列。交互提出按创建顺序追加，避免每次插入都改变已存在派生结果的相对顺序。主持早期草稿为最新在前、16 单位间距，此处根据质询明确修订。

收敛建议：源图 → 派生1 → 派生2 → 下一候选，24 世界单位间距；四个 creative slots 永不增加，display order 单独扩展。原图右邻是派生链；第一次结果紧邻源图，后续在该来源派生链尾追加。右侧四图预览仍是四候选，抠图另建有来源的结果卡。

### 3.5 退出蒙版是否每次确认？

用户提出默认保留草稿比每次弹出弃改对话更有把握。交互与产品接受：正常退出先真实保存草稿，成功后离开并提示；保存失败时才提供继续编辑、重试保存、放弃。全栈要求把本机草稿与服务端确认区分，不能以 `sendBeacon` 或内存中的草稿证明可靠保存。

本轮推荐默认保存退出；重复打开读取同一 MaskSession/MaskVersion，不重新识别。生成失败回蒙版也不自动 apply。最终按钮版本快照和幂等约束必须在服务端生效。

### 3.6 Python 迁移如何避免重写全部前端或同时写两套数据？

全栈建议继续使用已有 JS + Konva，将 Python 从当前 rembg 工具服务推进到领域 API 和独立 worker；SQLite 负责文档、任务、会话与事件，本地不可变文件存媒体。产品与交互要求新旧入口均能打开正确文档，后台完成不得覆盖用户修改。

收敛建议：契约与真实能力先行；副本迁移 dry-run；短暂停写并排空旧任务；校验 ID/hash/引用后切换；已迁移文档禁止旧 JSON API 写回。API 和 worker 共享同一 repository 规则，不能各自维护一份真相。新数据产生后，回滚不能简单覆盖旧备份。

## 6. 实施依赖与停止条件

1. **先核验能力与契约**：四方向语义、真实批次/并发、可编辑蒙版、真实 LLM 结构化计划。失败能力保持未就绪，不先美化入口伪装支持。
2. **建立 Python 持久底座**：schema、operation 幂等、revision、任务 lease、产物落位、outbox/SSE 游标。用 fake 上游和故障注入证明恢复。
3. **资产与迁移预演**：单写者、ID/hash/引用对账、不可变资产、旧数据只读兼容；切换和回滚在副本预演。
4. **入口与基础对象**：工作台列表、稳定地址、命名与返回、画板/文字、选框和浮层。
5. **四图与手动蒙版**：完成 W15–W17；两处预览复用同一资产；派生布局/失败/撤销/后台完成有完整验收。
6. **接入受限 Agent**：复用已验工具与操作层，加入真实计划、澄清、暂停、continuation、错误记录；聊天回复不能代替结果落位。
7. **视频、下载与综合验收**：资产链路、播放、重开、原文件下载；完成多标签、重启、断线及人工质量验证。

各阶段文件任务、DDL、API/事件样例、蒙版坐标和 alpha 算法、幂等与恢复事务、迁移回滚及实验指标详见技术方案。时间成本依供应商验证和迁移数据量估算，本轮不编造排期。

## 7. 分歧与推荐取舍

| 曾有分歧 / 可选方案 | 取舍 | 本轮推荐 |
| --- | --- | --- |
| 手动准备按钮 / 自动准备选区 | 显式按钮便于理解但增加一步；自动更短但要处理歧义和模式抢焦点 | 自动准备一次，严格范围校验；用户第三轮条件接受 |
| 单图协作抠图 / 主体加背景四方向 | 前者业务范围小但恢复完整；后者价值更丰富且依赖多 | 先单图用例，长链后置 |
| 补失败槽 / 另生完整四图 | 补槽更省调用但增加attempt/费用/版本复杂度 | 首版完整新组，清楚说明新调用 |
| 最新派生插源图后 / 派生按创建顺序 | 最新近源图但旧派生不断移位；追加稳定已存在顺序 | 源→派生1→派生2，24间距 |
| React整体重写 / 复用JS+Konva | 整体重写同时承担框架与领域迁移风险 | 复用引擎；维护成本升高后独立评估框架 |
| Express+Python工具 / Python领域核心 | 前者迁移少，后者可深化全栈任务/存储/Agent工程 | Python核心渐进迁移，禁止双写 |

没有将技术可实现视为生产已可用。剩余主要不确定性是供应商四方向能力、真实模型质量、可编辑蒙版与视频联通表现，属于需实验的能力边界。

## 8. 最多三个负责人决策

1. 是否采用单图协作抠图作为首条 Agent 完整用例？推荐采用。
2. 视频首版是否限定到已有生成入口、资产导入与预览下载？推荐限定。
3. 是否采用能力实验优先、Python核心渐进迁移、复用现有画布引擎的顺序？推荐采用。
